# Robotics Lab v0.3: robust MPC, torque-level control and Cartesian reaching

Branch `feature/mpc-v0.3-robustness`, 2026-10-17. Windows 11, Intel CPU, Python 3.13.7,
MuJoCo 3.16.0, OSQP 1.1.3, NumPy 2.5.4. Every number below was measured on this setup; raw
data is in `v0.3-benchmark-results.csv`, plots are in `figures/`, and the step-by-step
development record is in `v0.3-worklog.md`.

## 1. Initial technical problems (v0.2)

The v0.2 joint-space MPC drove the Menagerie Panda's **position servos**: the decision variable
is a joint-angle setpoint u, and MuJoCo applies tau = clip(kp (u - q) - kd qd, +-tau_max)
(kp up to 4500 Nm/rad, kd/kp = 0.1, tau_max = 87 / 12 Nm). v0.2 reported:

- worse tracking than the PID baseline on every moving trajectory (demo: 7.8 vs 3.4 mrad);
- actuator saturation on 21% of physics steps in the demo, from command-step torque spikes;
- 275 of 450 MPC updates falling back to PID in the wrist scenario;
- OSQP needing hundreds to thousands of iterations on some problems.

## 2. Audit of the v0.2 MPC (Stage 1)

| question | method | finding |
|---|---|---|
| Is the QP objective correct? | `tools/audit_mpc_objective.py`: 1/2 z'Pz + q'z vs term-by-term cost, random z | matches to 6e-14 (relative); dynamics and torque rows to 1e-14 |
| Is the linearization accurate? | rollouts vs prediction (v0.2 tests) | ~1e-6 rad over 0.4 s while torques stay unclipped |
| Conditioning? | eigenvalues, entry ranges | cond(P) = 8.8e3; constraint entries span 2.9e-7..167 (tiny ones are FD noise; zeroing them changes nothing) |
| Why do solves fail? | `tools/audit_fallback.py` on the first wrist fallback | no soft constraint active, yet 1775 iterations. The sustained torque kp(u_k - q_{k+1}) - kd qd_{k+1} hardly depends on u_k (d/du = -0.002..0.027): it cancels through the stiff servo. The effort term (weight up to 2.8e4) and torque rows act on that cancelling combination |
| Does it replan from the measured state? | tests | yes (perturbed state changes the command) |
| Real-time margin? | repeated runs | tracking metrics reproduce exactly; wall-clock does not: under CPU load 100 Hz overran 218 of 1200 updates |

**Implementation error found and fixed.** After a fallback, PID drives the servo every step,
but the next MPC update anchored its linearization point, command-rate penalty and **setpoint
slew limit** to its own stale last solution instead of the command actually being held.
The slew limit then pinned the new plan near a setpoint the servo no longer had, which made
the QP hard again, so fallbacks cascaded. Fix: anchor to the last command actually sent.
Wrist fallbacks fell from **275 to 43** of 450, and overruns from 236 to 31. With MPC really in
control, its honest wrist tracking is 3.1 mrad RMS / 47.8 mrad max. v0.2's 1.7 / 24.9 had
mostly been PID. A regression test fails on the v0.2 code.

Rejected mitigations (measured): looser tolerance (eps 1e-4: wrist max error 494 mrad, fallbacks
unchanged), lower effort weight (fallbacks unchanged), condensed QP (same solution in 475
iterations, but 94 ms per solve because the matrices are dense).

## 3. Mathematical control architecture

All controllers implement `compute(q, qd, q_ref, qd_ref, dt, t, qdd_ref)` and are called every
physics step (dt = 2 ms). MPCs re-solve every Ts = substeps * dt and hold their command between
updates (zero-order hold).

| controller | actuators | command | rate | model |
|---|---|---|---|---|
| A. `joint_pid` (v0.1) | position servos | setpoint q_ref + kp e + ki int(e) + 0.1 qd_ref | 500 Hz | none |
| B. `joint_mpc` (v0.2, bug fixed) | position servos | setpoint, QP over N = 15 | 50 Hz | MuJoCo linearization |
| C. `torque_ctc` | torque motors | tau = ID(q, qd, qdd_ref + Kp e + Kd e'), wn = 25 rad/s, zeta = 1 | 500 Hz | exact MuJoCo inverse dynamics (mj_inverse) |
| D. `torque_mpc` | torque motors | torque, QP over N = 25 | 50 Hz | MuJoCo linearization |

Both MPCs are **linear** MPC: the nonlinear MuJoCo dynamics are linearized once per update
around the measured state, and that linear model is used over the whole horizon. Neither
solves a nonlinear program.

## 4. Changes to the actuator model

`Panda(actuation="torque")` edits the spec in code (the vendored Menagerie XML is untouched):
actuators 1-7 get gain 1, no bias, `ctrlrange = forcerange = +-87 / +-12 Nm`. Masses,
inertias, armature (0.1), joint damping (1), joint limits, geometry and the gripper are
unchanged (tested field by field). The keyframe's arm controls are zeroed: they are joint
angles, which would otherwise become torques. Verified: `actuator_force == qfrc_actuator ==`
command, and commands beyond the limit are clipped at +-87 / +-12 Nm.

## 5. MPC prediction equations

State x = [q, qd] (7 arm joints), input u (setpoints for B, torques for D). At each update:

    A1, B1 = mjd_transitionFD(x0, u_hold)           one 2 ms step, forward differences
    A = A1^n,  B = (A1^(n-1) + ... + I) B1          n = Ts / dt substeps (arm block only)
    c = f_n(x0, u_hold) - A x0 - B u_hold            f_n: true n-step MuJoCo rollout
    x[k+1] = A x[k] + B u[k] + c,   k = 0..N-1

c makes the model exact at the linearization point (gravity, Coriolis, damping, armature).
Safeguards:
- **Finger rows.** The fingers sit on a joint limit, and composing the full 18-state matrix
  leaked finite-difference noise from them (spectral radius 1e22), so only the arm block is
  composed.
- **Force-clip discontinuity.** Under `implicitfast`, servo damping leaves the implicit update
  while the force is clipped, so the one-step map is discontinuous there. Jacobians straddling
  that boundary are replaced by those of a force-unlimited model copy.
- **Implausible models.** Any remaining implausible model triggers the fallback.

Prediction accuracy with torque inputs is lower than with servos, because there is no servo
holding the open loop: 16 mrad over 15 x 20 ms with random torques (10% of the motion), against
2 mrad over 15 x 10 ms.

**Torque MPC QP** (decision variables: normalized torques v = tau / tau_max):

    min  sum ||x_k - r_k||^2_Q (x5 at k = N) + w_e sum ||v_k - tau_g/tau_max||^2
         + w_r sum ||v_k - v_{k-1}||^2 + rho2 ||s||^2 + rho1 sum s
    s.t. dynamics;  -1 <= v_k <= 1  (hard: exact physical torque limit)
         q_min + 0.02 - s <= q_k <= q_max - 0.02 + s;  |qd_k| <= v_max + s;  s >= 0

Q = diag(1e5 (position), 10 (velocity)), w_e = 1, w_r = 10, rho2 = 1e3, rho1 = 1e6, N = 25,
Ts = 20 ms. Reference preview r_k = task reference at t + k Ts.

## 6. Constraint handling

| constraint | servo MPC (B) | torque MPC (D) |
|---|---|---|
| actuator torque | sustained torque at interval ends, soft; 1 ms command-step spikes left to MuJoCo's clip | **hard and exact** (the decision variable is the torque) |
| command | setpoint in ctrlrange + slew limit v_max Ts (hard) | same as torque |
| joint position | soft, 0.02 rad margin | soft, 0.02 rad margin |
| joint velocity (datasheet) | soft | soft |
| not enforced | acceleration/jerk limits, collisions, torque between knots | acceleration/jerk limits, collisions |

Numerics found while building D (measured):
- **Variable scaling.** With raw torques in Nm, P's diagonal spanned ~10 orders of magnitude,
  OSQP's polishing failed, and the at-rest plan drifted 2.7 mrad. With normalized torques,
  polishing succeeds, the drift is 1e-9 rad and the hold torque is exact to 6.5e-7 Nm.
- **Exact penalty strength.** Soft constraints only act as hard ones if the linear slack
  penalty exceeds the constraint multipliers. With rho1 = 1e5 a 2.5 rad step was planned at
  3.8x v_max; at 1e6 the slack is 6e-16 and the iterations drop from 1475 to 450.
- **Rate and horizon.** At 100 Hz with N = 30, solves overran the 10 ms budget under active
  constraints (~140 overruns), so the default is 50 Hz with a 0.5 s preview.

## 7. Benchmark methodology

`python benchmark.py` runs every controller on every scenario. All runs share the initial state
(home), environment (table), physics (dt = 2 ms, implicitfast) and reference trajectory. Metrics
are computed from the simulated robot at every physics step, never from controller predictions.
End-effector error is ||FK(q) - FK(q_ref)||: `site_xpos` read after `mj_step` is one physics
step behind `qpos`, so FK is used for both terms.

Scenarios: `demo` (3 s moves home -> left -> right -> home); `fast` (1 s moves, reference needs
1.4x v_max); `wrist` (large moves on the 12 Nm joints, also over-speed); `near_limits` (0.08-0.10
rad from joint limits); `reach` (Cartesian targets through IK, 1 out of reach); `demo_mismatch`
(model-based controllers get robot masses and inertias 15% too low; plant exact); `push` (30 N
sideways on the hand for 1 s while holding still).

**Comparison groups.** A/B use position servos; C/D use torque motors. A vs B and C vs D isolate
the controller. Comparisons across the groups change the actuator interface as well, so they
cannot be attributed to MPC alone.

| reach | 3.42 [3.48] | 0.079 [0.070] | 0.018 [0.005] | 0.031 [0.038] | **0.0022 [0.002]** |
| near_limits | 3.44 [3.50] | 10.8 [5.97] | 9.15 [5.55] | 0.093 [0.057] | **0.0038 [0.001]** |
| demo_mismatch | 3.42 [3.48] | 20.8 [2.09] | 6.52 [2.11] | 4.98 [3.05] | **1.91 [1.77]** |
| push | 3.44 [3.50] | 2.02 [2.19] | **1.74 [1.90]** | 35.2 [16.5] | 12.1 [9.12] |

| wrist (over-speed) | **3.44** | 47.8 | 13.7 | 0.29 | 532 |

Constraints and real-time behaviour:

| scenario | peak speed / v_max (A / B / C / D) | saturated steps B | fallbacks B / D | update p95 ms B / D |
|---|---|---|---|---|
| demo | 0.48 / 0.51 / 0.48 / 0.48 | 21% | 0/600 / 0/600 | 3.8 / 6.4 |
| fast | 1.43 / 1.06 / 1.43 / **1.0006** | 13% | 0/300 / 0/300 | 8.3 / 7.4 |
| wrist | 1.44 / 1.44 / 1.44 / **1.0007** | 25% | **43/450** / 0/450 | 17.9 / 7.3 |
| near_limits | 0.97 / 1.09 / 0.97 / 0.97 | 23% | 0/900 / 0/900 | 4.3 / 7.6 |

The deadline is 20 ms at 50 Hz. Deadline overruns: B 0-1 per run (wrist 1), B at 100 Hz 0-35
(wrist), D 0. Torque MPC never saturates (by construction); C and D used RMS torques within
0.5% of each other in every motion scenario (demo 15.64 / 15.64 Nm, fast 16.01 / 16.08 Nm).

Findings:

1. **Same actuator, torque level (C vs D).** Torque MPC tracks 14-25x more tightly than computed
   torque in demo/reach/near_limits (demo: 2.8 vs 63 urad) for the same RMS torque. It holds joints at
   their speed limit (1.0006x) where CTC follows over-speed references (1.43x). It degrades less
   under model error (1.9 vs 5.0 mrad; CTC never settles below 2 mrad). It is 3x stiffer against
   the push (12 vs 35 mrad). Both lack integral action.
2. **Same actuator, servos (A vs B).** PID still beats servo MPC on demo, near_limits, fast and
   wrist. Servo MPC is better on `reach` (79 urad vs 3.4 mrad), where speeds are low and no
   setpoint step saturates, and on `push`. That confirms the audit: the servo MPC's deficit
   comes from command-step saturation at speed, not from MPC as a method.
3. **Across actuators (A/B vs C/D).** The largest tracking gains come with the actuator change.
   Stiff servos remain better at rejecting an unmodeled push (A 3.4, B 2.0 mrad) than either
   torque controller (12-35 mrad). Torque control with perfect knowledge of its own model is
   not the same as robustness.
4. **Model mismatch.** Every model-based controller degrades with a 15% mass error (D: 2.8 urad
   -> 1.9 mrad; C: 63 urad -> 5.0 mrad; B: 7.8 -> 20.8 mrad). PID uses no model and is unchanged.
   Results with the exact plant model are an upper bound.
5. **Over-speed references** are a design trade-off, not a bug: MPC D obeys the limit and accepts
   large errors (169 / 532 mrad); PID and CTC follow the reference at 1.43x v_max.
6. **Cartesian reaching:** all controllers reach the three valid targets to 0.08 mm (the IK
   tolerance), and reject the out-of-reach and in-table targets with a reason.

Performance (Stage 5, median of 3 demo runs, per update): OSQP solve ~1.6 ms (B) / ~3 ms (D),
KKT refactorization after the matrix update 0.75 / 1.0 ms, linearization ~0.8 ms, Python
assembly ~0.6 ms. Forward-difference Jacobians (half the cost, within 1e-6) and in-place matrix
updates brought B from 3.67 to 3.35 ms; D (5.15 -> 5.08 ms) is dominated by OSQP. cProfile
misattributed solve time to `OSQP.update`; the per-call timing is the reliable measurement.

## 10. Known limitations

- **Perfect model.** Model-based controllers use the plant's own MuJoCo model; `demo_mismatch`
  shows how quickly this advantage shrinks. There is no friction, sensor noise, latency or delay.
- **No integral or disturbance estimation in torque control:** C and D deflect 12-35 mrad under
  the 30 N push. (The v0.2 disturbance estimator was for the servo MPC and hurt tracking.)
- **Linear MPC.** One linearization per update (LTI over 0.5 s); prediction error grows with the
  horizon. No nonlinear or sequential QP solve.
- **Servo MPC (B)** still saturates on 13-25% of steps at speed and falls back on 43/450 wrist
  updates; its residual hard QPs come from the near-uncontrollable sustained-torque term.
- **Reaching** is position-only IK (orientation free) and joint-space straight-line motion.
  Collisions are **checked, not avoided**: a target whose straight joint path hits an obstacle
  is rejected (demonstrated in the `obstacles` scene) rather than reached around it.
- **Timing.** Wall-clock timing is Python on desktop Windows and varied ~2x between sessions.
  Timings are indicative, not guarantees.

## 11. Recommended next experiments

1. Add integral action or a disturbance observer to the torque MPC (input-disturbance model)
   and re-run `push` and `demo_mismatch`.
2. Model-mismatch sweep (mass +-5..30%, damping, friction) and sensor noise / one-step delay.
3. Linear time-varying MPC (re-linearize along the previous plan) or SQP-RTI, to test whether
   the LTI approximation limits `fast`/`wrist`.
4. A 1 kHz inner torque loop (gravity compensation between MPC updates) to approximate
   hardware-style cascaded control.
5. Sampling-based joint-space planning (RRT-Connect against the existing collision checker) for
   reaching around obstacles, then pick-and-place.
