Our actual torque MPC implementation

A line-by-line account of TorqueMPCController (controllers/torque_mpc.py) and its prediction model (controllers/prediction.py). Every equation in this chapter corresponds to code; the source location is given under it.

Overview

The torque MPC is a linear, time-invariant-over-the-horizon, sparse-QP MPC with soft state constraints, hard torque limits, reference preview and an input-disturbance observer, re-linearized at every update from MuJoCo itself. At each update (every 10th physics step, i.e. 50 Hz) _update (line 295) performs:

  1. read the measured state $x_0 = (q, \dot q)$ and check it is finite;
  2. compute the gravity torque $\tau_g(q)$ and linearize MuJoCo around $(x_0, \tau_{\text{prev}})$: $A$, $B$, $c$;
  3. add the disturbance estimate to the model; form the references $r_1..r_N$ from the task preview;
  4. write the new numbers into the fixed-structure QP; warm-start OSQP; solve;
  5. keep the first torque as the held command; record statistics. On any failure, hand over to CTC.

State, control and decision vectors

Verified in source code
  • State: $x = (q_1..q_7, \dot q_1..\dot q_7) \in \mathbb{R}^{14}$ (self.nx = 2 * n, line 107). Fingers are not part of it.
  • Control: joint torques $\tau \in \mathbb{R}^7$ (Nm), held constant for $T_s$ = 20 ms (zero-order hold).
  • Decision variable for torques: the normalized torque $v_k = \tau_k / \tau_{\text{scale}}$ with $\tau_{\text{scale}} = (87, 87, 87, 87, 12, 12, 12)$ Nm, the largest absolute force limit per joint (line 114).
  • Full QP vector (comment at line 137): $z = [\,x_1, \dots, x_N \;|\; v_0, \dots, v_{N-1} \;|\; s_1, \dots, s_N\,]$, with one slack per state component per knot. For $N$ = 25: 350 + 175 + 350 = 875 variables.

Why normalize? The position weight is $10^5$ per rad² while an effort weight of 1 per (Nm)² on a 87 Nm joint is $1/87^2 \approx 1.3\times10^{-4}$ per raw Nm². The diagonal of $P$ would span about ten orders of magnitude. The v0.3 report measured the consequence: OSQP's polishing failed and the at-rest plan drifted 2.7 mrad. With normalized torques the drift is $10^{-9}$ rad (docstring lines 31–34; v0.3-results.md §6).

The prediction model

One physics step, differentiated by MuJoCo

MuJoCoPredictionModel.linearize(q, qd, u_lin) (prediction.py, line 245) uses the "power" method (_jacobians_power, line 270). It copies the live simulation state into private scratch data (positions, velocities, controls and the constraint solver's warm start; not the applied external forces, which a real controller cannot measure), overwrites the arm state and command, and calls mujoco.mjd_transitionFD, which returns the Jacobians of one complete 2 ms mj_step by forward finite differences with $\varepsilon = 10^{-6}$:

\[ A_1 = \frac{\partial x^{+}}{\partial x}\Big|_{x_0,\,u_{\text{lin}}}, \qquad B_1 = \frac{\partial x^{+}}{\partial u}\Big|_{x_0,\,u_{\text{lin}}} \quad (\text{arm block only, } 14\times14 \text{ and } 14\times7). \] prediction.py, _jacobians_power, lines 270–286

These are derivatives of MuJoCo's actual discrete step (implicitfast integration, armature, damping, the full rigid-body dynamics), not of a textbook ODE. Only the arm block is kept: the fingers rest on a joint limit, and finite differences across that limit once produced a spectral radius of $10^{22}$ when the full matrix was composed.

Composition over the control interval

Assuming the one-step Jacobians stay constant over the $n$ = 10 physics steps of one control interval, with the torque held constant:

\[ A = A_1^{\,n}, \qquad B = \left(A_1^{\,n-1} + A_1^{\,n-2} + \dots + A_1 + I\right) B_1 . \] prediction.py, lines 281–285 (loop: B_n = A1 B_n + B1; A_n = A1 A_n)

The affine term makes the model exact at the linearization point

A true 10-step MuJoCo rollout $f_n$ from $(x_0, u_{\text{lin}})$ is run, and

\[ c = f_n(x_0, u_{\text{lin}}) - A x_0 - B u_{\text{lin}} . \] prediction.py, linearize, lines 264–266

With this choice $x_1 = Ax_0 + Bu_{\text{lin}} + c$ equals the true MuJoCo state after one interval if the command is $u_{\text{lin}}$, so gravity, Coriolis and damping at the current state are included exactly, and only the change of command enters linearly. The linearization command is the last applied torque $\tau_{\text{prev}}$ (or $\tau_g$ before the first command; torque_mpc.py lines 305–307).

Safeguards

  • jacobians_plausible (line 124) rejects non-finite matrices, entries above $10^3$, or a spectral radius of $A$ above 2. If the true-model Jacobians fail, Jacobians of a copy with force limits removed (jac_model) are used; if those fail too, the update raises and the fallback takes over. The backup exists for the servo case, where the one-step map is discontinuous at the force-clip boundary.
  • The scratch data never writes the live MjData (test_prediction_never_modifies_live_state) and never sees xfrc_applied (test_external_forces_are_not_visible_to_the_model).

Offset-free model with the disturbance estimate

With the observer enabled (default), its current estimate $\hat d$ is treated as a constant known input over the whole horizon:

\[ x_{k+1} = A x_k + B\,(\tau_k + \hat d) + c \;=\; A x_k + B\tau_k + \underbrace{(c + B\hat d)}_{c'} . \] torque_mpc.py, _update, lines 311–313

The same $(A, B, c')$ is used for every stage $k = 0..N-1$: the model is linear time-invariant over the horizon. This is linear MPC, not nonlinear MPC.

The cost function, exactly as implemented

With $v_k = \tau_k/\tau_{\text{scale}}$ (element-wise), the torque that holds the arm still against gravity and the estimated disturbance $\tau_{\text{hold}} = \tau_g - \hat d$, its normalized version $v_{\text{hold}}$, and $v_{-1} = \tau_{\text{prev}}/\tau_{\text{scale}}$:

\[ \begin{aligned} J(z) = {} & \sum_{k=1}^{N} w_k\,(x_k - r_k)^T Q\,(x_k - r_k) \;+\; w_e\sum_{k=0}^{N-1}\|v_k - v_{\text{hold}}\|^2 \\ & +\; w_r\sum_{k=0}^{N-1}\|v_k - v_{k-1}\|^2 \;+\; \sum_{k=1}^{N}\left(\rho_2\|s_k\|^2 + \rho_1\mathbf{1}^Ts_k\right) \end{aligned} \] torque_mpc.py, _build_structure lines 151–171 (quadratic part) and _update lines 325–331 (linear part)

How the code builds it. The code writes $J = z^THz + 2h^Tz$ (constants dropped) and gives OSQP $P = 2H$ (upper triangle) and $q = 2h$, so OSQP's $\tfrac12 z^TPz + q^Tz$ equals $J$ minus a constant. $H$ is diagonal except for the torque-rate band: the diagonal entry for $v_k$ is $w_e + 2w_r$ (or $w_e + w_r$ for $k = N-1$) and the off-diagonal entries between $v_{k-1}$ and $v_k$ are $-w_r$ (expanding $\|v_k - v_{k-1}\|^2$). The linear part is $h_{x_k} = -w_k Q r_k$, $h_{v_k} = -w_e v_{\text{hold}}$ with an extra $-w_r v_{-1}$ on $v_0$ (the rate term against the previously applied torque), and $h_{s} = \rho_1/2$. The quadratic matrix $H$ is constant, so P is set up once; only q changes at each update. tools/audit_mpc_objective.py verified the analogous construction of the servo MPC term by term to $6\times10^{-14}$ (v0.3 report §2).

Interpretation

The effort term penalizes torque beyond what is needed to hold the arm still, not torque itself: holding against gravity is free. The rate term smooths the torque sequence and, through $v_{-1}$, penalizes jumps relative to the torque currently applied. With $Q_{\text{pos}} = 10^5$ and $w_e = 1$, a 1 mrad position error costs as much as a normalized torque deviation of 0.32, i.e. 27 Nm on a large joint: tracking dominates. This is also why the torque MPC is more sensitive to position noise than CTC (v0.4 report §5).

The constraints, exactly as implemented

\[ \begin{aligned} &\text{dynamics (equality):} && x_1 - \tilde B v_0 = A x_0 + c', \qquad x_{k+1} - A x_k - \tilde B v_k = c' \;\;(k = 1..N-1),\\ & && \text{with } \tilde B = B\,\mathrm{diag}(\tau_{\text{scale}}),\\ &\text{torque (hard):} && \tau_{\min}/\tau_{\text{scale}} \le v_k \le \tau_{\max}/\tau_{\text{scale}} \quad (\text{i.e. } -1 \le v_k \le 1),\\ &\text{state (soft):} && x_k + s_k \ge x_{\text{lb}}, \qquad x_k - s_k \le x_{\text{ub}}, \qquad s_k \ge 0. \end{aligned} \] torque_mpc.py, _build_structure lines 184–236; numeric blocks written in _update lines 317–323

with $x_{\text{lb}} = (q_{\min} + 0.02,\; -(1 - m)\,v_{\max})$ and $x_{\text{ub}} = (q_{\max} - 0.02,\; (1-m)\,v_{\max})$, where 0.02 rad is joint_limit_margin, $v_{\max}$ the datasheet speed limits, and $m$ = 0.005 the v0.4 velocity margin (default 0 in the class, 0.005 in default.yaml). The state constraints apply only at the knots $k = 1..N$, every 20 ms; nothing constrains the state between knots.

Fixed sparsity, changing numbers. The constraint matrix pattern is assembled once in COO form and converted to CSC; the code records where each stage's $A$ and $\tilde B$ entries land in OSQP's CSC data array (_a_idx, _b_idx). Each update overwrites only those entries and the bounds, and calls solver.update(q=…, l=…, u=…, Ax=…). Because the matrix values change, OSQP must refactor its KKT system at every update, measured at 18–22% of the update time (v0.4 report §7). Before updating, the code checks that all data are finite and $l \le u$, because OSQP 1.x silently ignores inconsistent bounds and returns the old solution (CLAUDE.md, "MPC facts").

Solver settings and warm start

  • Accepted statuses: solved and solved inaccurate (line 68). Anything else, or a non-finite solution, raises.
  • Warm start (_shifted, line 372): the previous solution shifted by one interval (states, torques and slacks move one stage earlier; the last stage is repeated) is given to OSQP as the starting point. Mean iterations were 45 on the demo motion (v0.4 report §7) and 37.7 in the traced demo run of Chapter 3.
  • Rejected alternatives (measured): looser tolerance $10^{-4}$ needed more iterations; turning polishing off was 25–30% faster but raised demo error from 2.8 to 29.6 µrad (v0.4 report §7).

How the reference reaches the controller

The controller never imports tasks. The runner passes a callable reference_preview(t) that returns the task's $(q_{\text{ref}}, \dot q_{\text{ref}})$ at any time $t$ (SimulationRunner._reference_preview). At each update, _references (line 284) evaluates it at $t + kT_s$ for $k = 1..N$, giving the 25 future reference states $r_k$; the task's reference acceleration is not used by the MPC. Without a preview function the controller would extrapolate the current reference linearly. The preview means the MPC "sees" corners of the trajectory 0.5 s before reaching them.

Between updates: holding, feedthrough and the observer

compute (line 264) is called every 2 ms:

  1. observer.update(q, qd, dt) folds in the newest measurement (every step, 500 Hz);
  2. if self._step % substeps == 0, run _update;
  3. output the held MPC torque, corrected by the change of the disturbance estimate since the last update:
\[ \tau(t) = \mathrm{clip}\!\left(\tau_{\text{MPC}} - \big(\hat d(t) - \hat d_{\text{update}}\big),\; \tau_{\min},\; \tau_{\max}\right) \] torque_mpc.py, compute, lines 275–278 (disturbance_feedthrough = true in default.yaml)

This 500 Hz inner correction matters: with a 10 ms observer but without feedthrough, the push error was 7.1 mrad instead of 3.75 mrad, because the torque is otherwise frozen for 20 ms (v0.4 report §5).

Failure handling

Any exception inside _update (non-finite state, implausible linearization, inconsistent QP data, solver status not accepted) sets _using_fallback = True and clears the warm start. Until the next successful update, compute returns the fallback's command: plain computed-torque control (no observer, no integral), built by build_ctc(..., fallback=True). The applied command is always recorded in _applied, and the next linearization and rate term are anchored to it. That design comes from the one implementation bug the project found in its MPC line: in v0.2 the servo MPC anchored to its own stale solution after a fallback, which cascaded into 275 fallbacks out of 450 updates; anchoring to the applied command reduced them to 43 (v0.3 report §2). In the traced demo run there were 0 fallbacks.

How the torque reaches MuJoCo

SimulationRunner.step passes the returned 7-vector to engine.set_arm_command, which clips it to ctrlrange (±87/±12 Nm) and writes data.ctrl; mj_step applies it through the torque-motor actuators (gain 1, no bias), so actuator_force equals the command (test_torque_command_is_applied_force). Note one idealization: the command computed from the state at time $t$ is applied at time $t$, although on hardware the 4–5 ms of computation would delay it.
