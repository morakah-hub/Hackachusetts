Testing and validation

How the 189 automated tests work, what kinds of claims they support, and which important behaviours they do not check.

How the tests run

The tests use pytest: every function named test_… in tests/ is collected and run; assert statements decide pass or fail; @pytest.mark.parametrize runs one function for several inputs (15 such decorators expand 157 test functions into 189 collected tests). Fixtures with scope="module" build expensive objects (engines, planners) once per file. All tests are headless; the one offscreen-render test skips if no OpenGL context exists. The full suite took 1 min 57 s to 2 min 44 s in the v0.5.2 session (.\.venv\Scripts\python.exe -m pytest tests -q).

Benchmarks are not tests. The benchmark scripts measure performance and write numbers; they assert nothing about the numbers. Tests assert properties (often with generous thresholds, such as "tracking error below a bound") so that they are robust to small numerical changes.

Mathematical guarantees versus empirical observations

A test can only check finitely many cases. Some tests check a property that is also proven (the lever-arm bound holds for every posture by the triangle inequality; the test confirms the implementation matches the proof on random edges). Others check an observation with no proof behind it (that the torque MPC tracks the demo below a threshold; that the checker agreed with mj_geomDistance on 500 configurations). Neither kind proves correctness in general. The project's documentation is careful about this distinction; the planner's "15 mm" is a deduction with assumptions (Chapter 11), and the controllers' stability is empirical (Chapter 8).

What the tests do not validate

Gaps
  • Real-time behaviour. No test checks timing; deadline overruns are only reported by benchmarks.
  • Quantitative benchmark claims. The numbers in the reports are not asserted anywhere; a regression that worsened tracking from 2.8 µrad to 50 µrad could pass the suite if it stays under a test's threshold.
  • Viewer mode. run_viewer and its Windows thread-join workaround are not exercised (only path drawing into a scene, headless).
  • Self-collision between samples, and robot–environment clearance during execution beyond the specific runs tested.
  • Breadth of scenarios. Planning tests use a few scenes and starts; there is no randomized scenario generation or long-run statistics.
  • Realistic sensing. Only white Gaussian noise; no quantization, delay, filtering, or dropped measurements.
  • Model error beyond mass scaling (friction, damping, armature, centre of mass).
  • Servo MPC quality. Tests check it runs and falls back correctly, not that it tracks well (it does not, compared with PID).
  • Optimality of QP solutions for the torque MPC (the objective audit tool exists only for the servo MPC).
  • Documentation commands. Commands in README/reports are not executed by tests.
  • Grasping, pick-and-place, perception, replanning during motion: not implemented, hence not tested.
