What happens when you run main.py?

A complete trace of one run, from the command line to the final printout, with the file and function that does each step. We follow the most complete path through the code: the wall-avoidance demo with torque MPC.

The command traced in this chapter is

.\.venv\Scripts\python.exe main.py --config configs\planning_demo.yaml --headless

It reaches two Cartesian targets on either side of a wall with motion planning enabled, using the torque MPC controller, and prints a summary instead of opening the viewer. Its actual output on the documented commit (run on 19 Oct 2026, saved in results/v0.5.2_demo_headless.txt) was:

By the end of this chapter every line of that output should make sense. summarizes the flow.

Program start-up

main() (main.py, line 23) defines the command-line options with argparse: --config, --environment, --headless, --duration, --controller {pid, mpc, ctc, torque_mpc}, --control-rate, repeatable --target X Y Z, --planning/--no-planning, --plan-seed and --unchecked-direct. Importing main.py already imports the runner, which imports every controller, task and planner module, and MuJoCo itself (a compiled C library with Python bindings).

Configuration loading

load_config(path) (simulation/runner.py, line 76) reads the YAML file. configs/planning_demo.yaml starts with extends: default.yaml, so the default file is loaded first and the demo file is merged over it recursively (_merge), with one special rule: the task section is replaced as a whole, not merged. The merged configuration contains environment: planning_demo, a cartesian_reach task with a start configuration and two targets, a planning section (clearance 0.02 m, RRT budgets, IK seeding, exact_box_box: true), controller.type: torque_mpc and, inherited from the default, all the torque-MPC weights and the disturbance-observer settings. Command-line options then overwrite entries of this dictionary (lines 55–88 of main.py): for example --controller ctc sets config["controller"]["type"] = "torque_ctc", and --no-planning sets task.planning.enabled = False.

Robot model loading

SimulationRunner.__init__ (runner line 224) first decides which actuator model the controller needs: CONTROLLER_ACTUATION["torque_mpc"] = "torque". It constructs Panda(actuation="torque") and passes it to the engine. Inside build_spec (simulation/engine.py, line 53) the robot description loads the Menagerie XML as an MjSpec (Panda.load_spec), adds the ee_site, and converts actuators 1–7 to torque motors: gain 1, no bias (so the applied torque equals the command), command range equal to the force range (±87 Nm, ±12 Nm), and the home keyframe's commands set to zero (they were joint angles, which would otherwise be interpreted as torques).

Environment initialization

Still in build_spec, the environment file environments/planning_demo.xml is loaded into its own spec; geometry overrides would be applied here (none in this run); the robot's base body is attached to a frame at the robot_mount site (0, 0, 0.40), i.e. on the table top; and a contact exclusion between link0 and table is added because the base rests on the table. spec.compile() produces the MjModel (nq = 9 position coordinates: 7 arm joints and 2 finger slides; nu = 8 actuators), and MjData holds the changing state. The engine caches index arrays and limits and calls reset(), which loads the home keyframe and runs mj_forward so every derived quantity (link poses, contacts) is consistent. The scene contains the floor, the table (top and four legs) and the wall, a box 0.55 × 0.04 × 0.26 m.

Task creation

_build_task (runner line 291) sees type: cartesian_reach with planning enabled. It builds an ArmKinematics object (IK with joint-limit margin 0.05 rad and damping 0.05), then the motion planner through MotionPlanner.from_engine, which creates a CollisionChecker on a deep copy of the compiled model (Chapter 11). It then constructs CartesianReachTask(targets, start, plan=planner.plan_to_position, …). The task's constructor (tasks/reach.py, line 41) immediately calls plan(target, q_from) for each target in order, starting from the configured start configuration [0.246, 0.621, 0.211, −1.791, 0.089, 1.756, −0.785], which puts the hand at (0.45, 0.25, 0.50) m on the left of the wall. So planning happens during object construction, before the simulation starts.

Inverse kinematics

plan_to_position (planning/motion_planner.py, line 129) first checks that the start configuration is valid, then calls ik_candidates (planning/ik.py). That function runs damped-least-squares IK (ArmKinematics.solve_ik) from 22 seeds: the current configuration, the rest posture, 8 random perturbations of the current configuration (σ = 0.5 rad) and 12 uniformly random configurations. Each converged solution (position error below 0.1 mm) is checked by the collision checker; valid ones are sorted by weighted joint distance from the start, near-duplicates are merged, and at most 4 are kept. Chapter 4 explains the IK mathematics.

Motion planning

For the first IK candidate the planner calls RRTConnect.plan(q_from, q_goal, seed) (planning/rrt_connect.py, line 146). It first checks the straight joint-space edge: here it is blocked (the hand would sweep through the wall), which is what the output means by "direct edge BLOCKED". The two random trees then grow until they connect (21 nodes for the first target, 3,910 collision checks including IK validation and shortcutting), the path is reconstructed, and shortcut shortens it from 4.39 rad of joint motion to 1.41 rad with 4 vertices (start, two via points, goal). Each query gets a deterministic seed: 0 for the first target and 1000 for the second (_next_seed). The returned MotionPlan carries the path, the raw path and statistics. If planning had failed, the target would be marked rejected with the reason and skipped; the straight move is never substituted.

Trajectory generation

Back in CartesianReachTask, the path's interior vertices become via points: waypoints with zero hold time. The goal gets a 1.5 s hold. The task then builds one internal JointTargetTask with per-move durations: each planned edge requests segment_time = 1.0 s. For every edge, plan_segment (tasks/trajectory.py, line 189) computes the minimum-jerk timing along the straight joint line and lengthens it if 90% of the velocity limit, 50% of the acceleration limit, 5% of the jerk limit or 80% of the torque limit (checked with inverse dynamics of the controller's model at 101 samples) would be exceeded. The reference therefore stops at each via point and moves along exactly the edges the collision checker validated. The total duration of this run is 9.0 s (2 × 3 edges of ≥ 1 s plus 2 × 1.5 s holds).

Controller initialization

build_controller → build_torque_mpc (runner line 163) creates:

  • a MuJoCoPredictionModel on the controller's model with substeps = 10 (50 Hz control on a 500 Hz simulation, checked by control_substeps);
  • a ComputedTorqueController as fallback (plain CTC, no observer);
  • a JointDisturbanceObserver with time constant 10 ms (enabled in default.yaml);
  • the TorqueMPCController with horizon 25, the weights from the config and the reference_preview callable that lets the MPC ask the task for the reference at future times.

The controller's constructor builds the sparsity pattern of the quadratic program once (_build_structure), so later updates only overwrite numbers. Finally runner.reset() puts the robot at the task's first waypoint (the start configuration), opens the gripper (command 255) and places the red target marker.

Repeated control optimization

run_headless(9.0, before_step=count_contacts) loops 4,500 times. Each iteration calls SimulationRunner.step() (runner line 358), which asks the task for the reference at the current simulated time and calls controller.compute(q, qd, ref.q, ref.qd, dt, t, qdd_ref). Inside TorqueMPCController.compute (controllers/torque_mpc.py, line 264):

  1. the observer folds in the newest measurement and updates its disturbance estimate (every step);
  2. on every 10th call, _update linearizes MuJoCo around the measured state, writes the new model and references into the QP, warm-starts OSQP with the previous solution shifted by one interval, and solves; the first torque of the solution becomes the held command;
  3. between updates the held torque is returned, corrected by the change in the disturbance estimate since the last update (feedthrough).

In this run there were 450 updates (9 s × 50 Hz), all solved, with a mean of 37.7 OSQP iterations and a mean update time of 4.86 ms against a 20 ms budget. Chapter 8 dissects _update.

Applying motor commands

engine.set_arm_command(tau) clips the seven torques to the actuator command range and writes them into data.ctrl. With torque motors, the force MuJoCo applies equals this command. The gripper command (255, open) stays constant; nothing in this task closes it.

Physics simulation

engine.step() calls mujoco.mj_step, which computes the forward dynamics (inertia, Coriolis and gravity forces, joint damping, armature, actuator forces, contact forces if anything touches) and integrates 2 ms forward with the implicitfast integrator (Chapter 5). This is the only way the robot moves: the project rule "never set qpos/qvel to produce motion" is enforced by tests (test_arm_moves_only_through_actuators).

Feedback measurements

At the next iteration engine.arm_qpos() and arm_qvel() copy the joint angles and velocities out of MjData. These are the controller's measurements; the loop is closed because the next command depends on them. They are perfect (no noise) unless the configuration has a sensor_noise section, in which case the runner adds seeded Gaussian noise to what the controller sees, while metrics still use the true state.

Task completion

Nothing "finishes" in the control loop: the task simply returns the final waypoint with zero velocity after its last segment (for non-looping tasks), and the loop stops after duration simulated seconds (by default the task's duration, 9.0 s). There is no success detection inside the loop; success is judged afterwards from the log. If a target had been rejected, it would never have entered the reference.

Logging and evaluation

run_headless appends a sample to a RunLog every 10 steps (time, q, q_ref, the end-effector position, velocities, the reference acceleration, commands and applied actuator forces), giving 450 samples. main.py then prints the maximum joint tracking error over the log (rounded to 4 decimals, it shows 0.0000 rad, i.e. below 0.05 mrad; the planning benchmark measured 31 µrad for torque MPC on this scene, docs/research/v0.5-results.md §8), the final configuration and end-effector position, the contact count collected by count_contacts every step, the end-effector error at the end of each hold, and the MPC statistics from controller.stats.summary().

Caution: what "deadline overruns" means in simulation

The MPC counts an update as an overrun when its wall-clock time exceeds the 20 ms control period. In headless mode simulated time does not wait for wall-clock time, so an overrun has no effect on the motion: the simulator simply waits for the solver. In viewer mode the loop sleeps only when the simulation is ahead of the wall clock (_viewer_loop), so slow updates make the animation run slower than real time, but again do not change the physics. Overruns are therefore a warning about real-time feasibility on hardware, not a failure in the simulation (Chapter 9).
