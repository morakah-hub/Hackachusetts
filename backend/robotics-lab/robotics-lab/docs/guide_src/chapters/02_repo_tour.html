Discrepancy found while reading

tasks/pick_place.py exists but is empty (0 lines) since the very first commit (184bfd6). Nothing imports it. It marks a planned feature, not an implemented one. Likewise, the module docstring of simulation/runner.py says the controller is "joint_pid or joint_mpc", but the code supports four types (CONTROLLER_TYPES also has torque_ctc and torque_mpc); the docstring was not updated in v0.3. The comment in configs/default.yaml lists the environments as "table | empty | obstacles" and omits the two planning scenes, which do work.

The architecture at a glance

The code follows one rule stated in CLAUDE.md: modules are separated by role. Environments know nothing about robots; tasks only produce references; controllers only produce actuator commands; the planner runs before motion and is invisible to the controllers. shows how the pieces connect during a run.

robots/ and environments/

robots/panda.py defines the frozen dataclass Panda, a name-level description of the robot: joint names (joint1…joint7), actuator names, the base body link0, the end-effector site ee_site, the home pose HOME_QPOS, and the datasheet velocity, acceleration and jerk limits. Its method load_spec() loads the Menagerie XML into an editable mujoco.MjSpec, adds the end-effector site 0.1034 m below the hand body (between the fingertips), and, for actuation="torque", calls _make_torque_actuators, which rewrites actuators 1–7 from position servos to direct torque motors with the same force limits. Input: the actuation choice. Output: an MjSpec. Used by: SimulationEngine and the tests.

environments/*.xml are MuJoCo scene files. Each must provide a robot_mount site, a mocap body named target (the red marker sphere, which cannot collide), and the implicitfast integrator with a 2 ms timestep. They are pure data and are read by build_spec.

simulation/

engine.py — SimulationEngine. build_spec(environment, robot, overrides) loads the scene, applies optional geometry overrides (v0.5.1), attaches the robot at the mount site, and excludes base-table contact. The constructor compiles the model and creates MjModel/MjData, then caches index arrays: arm_qpos_adr, arm_dof_adr (where the arm joints live in MuJoCo's state vectors), actuator ids, joint limits and command limits. Methods: reset(arm_qpos) (the only place joint positions are written), arm_qpos(), arm_qvel(), ee_position(), set_arm_command(ctrl) (clips to the actuator command range), step(), apply_external_force() (for push tests), perturbed_model(mass_scale) (a copy with wrong masses for mismatch experiments), forward_kinematics(q) and robot_contacts(). The attribute controller_model is the model handed to model-based controllers; it equals the plant model unless a mismatch experiment replaces it. Used by almost everything.

runner.py — SimulationRunner is the composition root: the one place that knows about every other module. load_config reads YAML with single inheritance (extends:). build_controller and its helpers (build_pid, build_mpc, build_ctc, build_torque_mpc, build_observer) construct controllers from config. The runner's _build_task builds the task (and the planner if enabled); step() is the control loop body; run_headless() returns a RunLog; run_viewer() opens MuJoCo's passive viewer and paces the simulation to wall-clock time. Chapter 3 walks through it line by line.

kinematics.py — ArmKinematics computes forward kinematics (fk, fk_pose), the 3×7 end-effector Jacobian (jacobian, via mj_jacSite), damped-least-squares inverse kinematics (solve_ik), contact queries (contacts, path_contacts) and the v0.3 "IK + straight-path collision check" planner plan_target. It also provides rotation_angle for orientation metrics. It always works on private scratch data. Used by the runner, the planner (planning/ik.py), the benchmarks and the video tool.

benchmark.py, planning_benchmark.py, robustness.py are experiment drivers. They build runner configurations for each (controller, scenario) or (scenario, seed) pair, run them headless, compute metrics from the simulated robot (never from controller predictions) and write CSV/JSON/Markdown/plots to results/. robustness.py also defines ExactClearance, an independent distance measurement with mj_geomDistance over every robot–environment geom pair. Chapter 15 covers the experiments.

tasks/

A task turns a description of the goal into a reference: a function of time returning a Reference(q, qd, waypoint_index, qdd). Tasks never touch the simulation.

  • JointTargetTask (joint_target.py): moves along straight joint-space lines between waypoints, each move timed by plan_segment and followed by a hold. Optional per-move durations (move_times, hold_times) support planned via points. Can loop.
  • trajectory.py: the timing laws (quintic, DoubleS), KinematicLimits, plan_segment (lengthens a move until velocity, acceleration, jerk and torque limits hold, or raises TrajectoryInfeasible) and check_reference.
  • CartesianReachTask (reach.py): resolves each (x, y, z) target through an injected plan function (either IK + straight-path check, or the motion planner), skips unreachable targets with a reason, and builds an internal JointTargetTask.
  • PlannedJointTask (planned_joint.py): like JointTargetTask but each move follows a planned path; raises PlanningFailed if any move cannot be planned.

planning/

  • CollisionChecker (collision.py): is a configuration valid (inside joint limits minus 0.05 rad, no contact, ≥ 20 mm from the environment)? Is a straight edge between two configurations valid at all its samples? Works on a private deep copy of the model with contact margins, midphase disabled, and (since v0.5.2) exact distances for box-box pairs. Chapter 11.
  • RRTConnect (rrt_connect.py): the bidirectional rapidly-exploring random tree planner with time/node/iteration budgets. Chapter 10.
  • shortcut, prune (shortcut.py): shorten a valid path while keeping it valid.
  • ik_candidates (ik.py): many IK solutions from different seeds, filtered by the checker, sorted by distance from the start.
  • MotionPlanner (motion_planner.py): facade with plan_joint(q_start, q_goal) and plan_to_position(target, q_from) returning a MotionPlan; PlanningSettings.from_config parses the YAML section.
  • visualization.py: draws the planned end-effector curves into the viewer scene (green executed, orange raw). Visual only.

Who depends on whom

The import graph (computed from the source with grep) has a clear layering with a few exceptions that Chapter 13 analyses:

  • robots → nothing in the project; simulation/engine → robots.
  • controllers → only controllers (and MuJoCo); they never import tasks, planners or the engine. The MPC gets future references only through a callable injected by the runner (reference_preview).
  • tasks → only tasks; the planner is injected as a function.
  • planning → planning and simulation/kinematics (for IK).
  • simulation/runner → everything (composition root); main.py and the benchmark drivers → runner.
  • Exceptions: torque_mpc.py imports private helpers (_per_joint, MPCStats, plan_violations) from the servo mpc.py; planning_benchmark.py and robustness.py import each other (one import is deferred inside a function to avoid a cycle); controllers/__init__.py still exports only the v0.2 classes.
