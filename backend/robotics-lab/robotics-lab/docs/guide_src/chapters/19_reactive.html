Reactive planning and autonomous manipulation

How the existing pieces (torque MPC, planner, trajectory generator, collision checker) could be combined with perception, safety monitoring, replanning, grasping and high-level decision making, and the engineering problems that stand in the way. All of it is proposal.

Status

None of the architecture in this chapter is implemented. It is a design discussion grounded in the current code.

A layered autonomy stack

World-model updates and reactive replanning

With perception updating the world model, a monitor would re-check the remaining part of the current path at every world-model update (cheap: path_valid on a few edges; tens of milliseconds at the measured 35–67 µs per configuration check). If it becomes invalid, three responses are possible, in increasing sophistication: stop safely; replan from the current state; or locally deform the trajectory. Replanning from a moving state is the hard part: today's planner assumes a start at rest at a waypoint.

Trajectory updates and controller continuity

Swapping in a new trajectory while the arm moves must not create a jump in the reference, or the MPC will see a step and the torque will jerk. Standard approaches: start the new plan from the state predicted at the switching time (position and velocity), blend over a short window, or plan with the current velocity as an initial condition. The torque MPC helps here: its reference preview means a new reference can be fed in through reference_preview without restarting the controller, and its warm start keeps the optimization continuous. Today's rest-to-rest segments cannot represent a non-zero starting velocity.

Safety monitoring and safe stopping

A safety monitor is an independent, simple layer that can override everything above: if the predicted state violates a limit, the measured distance to an obstacle drops below a threshold, or the planner fails to deliver, it commands a controlled stop. A controlled stop needs a stopping trajectory that is itself feasible (speed and torque limits) and collision-free; with the current speeds the stopping distance is short but not zero. The MPC could implement "stop" simply as a reference that holds the current position, with its torque limits guaranteeing feasibility of the command (not of the stop distance).

Obstacle-aware MPC

An alternative to replanning is to give the MPC itself obstacle constraints, for example linearized distance constraints $d(q_k) \ge c$ approximated as $d(\bar q_k) + \nabla d(\bar q_k)^T(q_k - \bar q_k) \ge c$ around the previous plan. This keeps the QP convex but is only locally valid, and the 0.5 s horizon cannot find detours around large obstacles. In practice it complements a global planner (the planner finds the route; the MPC keeps a margin locally). It would require distance gradients, which MuJoCo can provide through mj_geomDistance's witness points.

Grasp planning and contact-rich manipulation

Grasping adds requirements the current system lacks:

  • Orientation. IK must solve for the full hand pose (6-D), not just position.
  • Intentional contact. The collision checker must allow fingers to touch the object being grasped (contact exclusions per phase).
  • Gripper control. Actuator 8 must close with controlled force; finger states are currently frozen in the prediction and collision models.
  • Changing dynamics. A grasped object changes the arm's payload. The disturbance observer would partially absorb an unknown payload (it did for a 30 N downward load ≈ 3 kg, Chapter 9), and the object must join the robot's collision geometry.
  • Contact-rich control. Pushing, inserting or wiping need force or impedance control (regulating contact forces rather than positions), which neither the CTC nor the MPC currently provides.

High-level AI agents

A language-model or learned task planner could decide what to do ("clear the table") and emit goals to the motion layer. The clean interface is narrow: goals (target poses, grasp/release commands) go down; status (reached, rejected with reason, failed) comes up. The existing motion layer already returns explicit rejection reasons ("collision on path", "IK did not converge"), which is exactly the kind of feedback such an agent needs. Safety must remain in the lower layers: an agent's request should never bypass the collision checker or the torque limits.
