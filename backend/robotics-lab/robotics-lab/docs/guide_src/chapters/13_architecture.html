Software architecture and modularity

Which parts of the code could be swapped out cleanly, which are merely in separate files, and which are tightly bound to the Panda and to MuJoCo. The second half asks what it would take to substitute major components; everything there is a proposal.

The intended layering

The project's stated rules (CLAUDE.md, "Conventions and rules") are: environments know nothing about robots; tasks produce references only; controllers produce actuator commands only; settings belong in YAML; the prediction model never writes live simulation data; motion comes only from data.ctrl + mj_step. The import graph (Chapter 2) shows these rules are largely respected.

What is truly modular

  • Controllers behind one interface. All four implement Controller.compute(q, qd, q_ref, qd_ref, dt, t, qdd_ref) and reset(); the runner and benchmarks treat them uniformly; a new controller needs one class and one branch in build_controller. Controllers never import tasks, planners or the engine; future references arrive through the injected reference_preview callable.
  • Tasks as reference generators. Every task exposes reference(t), duration, waypoints and timing information (an implicit, duck-typed interface; there is no abstract base class). The planner is injected as a function (plan=planner.plan_to_position), so tasks do not depend on planning/.
  • Environments independent of robots. Scene files only need a robot_mount site and a target mocap body; the robot is attached in code.
  • Configuration-driven runs. Environment, task, controller, planner settings, mismatch, noise and geometry overrides all come from YAML, so experiments are data, not code.
  • Planner invisible to controllers. Planning produces an ordinary joint reference; the same plan runs under any controller.

What is only separated into files

  • The robot. Panda is a dataclass of names and limits, and SimulationEngine reads its fields (joint names, actuator names, base body, end-effector site). But Panda specifics leak elsewhere: the end-effector offset, the gripper command 255, the actuator conversion in _make_torque_actuators (assumes seven general actuators with a home keyframe), the finger handling in the prediction model (it composes only the arm block), and the 7-joint shapes assumed in tests and configs.
  • Controller selection. CONTROLLER_TYPES, CONTROLLER_ACTUATION and the build_* functions in runner.py are a hand-written factory; adding a controller means editing the runner.
  • Experiment drivers. The three benchmark modules share patterns (config building, CSV writing) but not code; they import specific controller classes to read their statistics.

What is tightly coupled

  • MuJoCo everywhere. The prediction model (mjd_transitionFD, rollouts), inverse dynamics (mj_inverse), the observer (mjENBL_INVDISCRETE), kinematics (mj_kinematics, mj_jacSite), the collision checker (mj_collision, mj_geomDistance, margins, midphase flag) and the benchmarks all take MjModel/MjData directly. This is a deliberate strength (the controller model is exactly the simulator's dynamics) and the main obstacle to changing simulator.
  • Torque MPC on servo-MPC internals. torque_mpc.py imports MPCStats, MPCUpdate, plan_violations and the private helper _per_joint from mpc.py.
  • Planning on simulation code. planning/ik.py and motion_planner.py use simulation.kinematics.ArmKinematics, and the checker is built from a SimulationEngine (from_engine).
  • Benchmark cycle. simulation/robustness.py imports planning_benchmark, which imports robustness lazily inside a function for ExactClearance.
  • Special names. The engine excludes contact between the robot base and a body literally named table.

Recommended interfaces for future work

Proposals
  • RobotDescription protocol: dof, joint/actuator names, limits (position, velocity, acceleration, jerk, torque), end-effector frame, home pose, load_spec(actuation). Removes Panda constants from the engine and prediction model.
  • DynamicsBackend: step, get_state/set_state, inverse_dynamics, linearize(x, u, substeps), gravity. Implemented once for MuJoCo; the controllers would depend on it instead of on MuJoCo directly.
  • CollisionWorld: min_distance(q), in_collision(q, clearance), update_geometry(obstacles); the checker's edge logic (lever arms, sampling) stays above it. A perception module would write into it.
  • Planner protocol (exists informally): plan_joint, plan_to_position → MotionPlan; allows RRT*, learned planners or trajectory optimization side by side.
  • Task abstract base class formalizing reference(t), duration, timing_report; plus an event interface (target reached, replanning requested) that the current open-loop task sequence lacks.
  • Move shared MPC statistics into a neutral module (e.g. controllers/mpc_common.py) and ExactClearance into planning/ to remove the two cross-layer couplings.
