Robotics Lab

Complete Technical Guide
A Franka Emika Panda arm simulated in MuJoCo: kinematics, dynamics, feedback control, torque-level model predictive control, sampling-based motion planning, collision checking with clearance, trajectory generation, and the experiments that test them. Written for a reader who knows calculus and basic mechanics and wants to reach a research-level understanding of this specific code base.
Repository state documented: branch feature/v0.5.2-clearance-fix, commit 5dbeffd (v0.5.2), 19 October 2026.
Software: Python 3.13, MuJoCo 3.16.0, NumPy 2.5.4, SciPy 1.18.1, OSQP 1.1.3, Windows 11.
Every statement about the software is checked against the source code at that commit; numerical results are quoted from the project's own research reports and data files, with their sources.

How to read this guide

This guide has two jobs. It teaches the robotics, control and planning ideas that the project uses, starting from first-year engineering mathematics. It is also an accurate reference to the code itself: every class, equation and number is tied to a file in the repository so you can open it in VS Code and check.

Who it is written for

You know calculus I–III, Newton's laws, moments and simple differential equations, and some Python or MATLAB. You do not need to know robotics, control theory, optimization or motion planning yet. Each chapter starts with intuition, explains why the idea matters, develops the mathematics at an accessible level, connects it to our code, gives an example from this project, and ends with its limitations. Later chapters (7, 8, 11, 20) go to the level of a graduate course or a research paper.

The four kinds of statements

Robotics write-ups often blur "the code does this", "an experiment showed this", "the math implies this" and "we could do this". This guide keeps them apart with coloured boxes:

Verified in source code

A fact read directly from the repository at commit 5dbeffd. The file and function are named, for example controllers/torque_mpc.py TorqueMPCController._update.

Reported experimental result

A number measured by one of the project's experiments, quoted from its research report or CSV file (docs/research/…). It holds for the stated conditions, sample size and machine. This guide did not re-run the large benchmarks; it quotes them.

Mathematical deduction

A conclusion that follows from equations, together with the assumptions it needs. If an assumption fails, so does the conclusion.

Proposal (not implemented)

An idea for future work. Nothing in such a box exists in the code today.

Discrepancy or caution

A place where documentation and implementation disagree, or where a common misunderstanding is likely. These are investigated, not hidden.

Conventions

  • Vectors are bold-free but clear from context: $q \in \mathbb{R}^7$ is the vector of the seven arm joint angles, $\dot q$ its time derivative (joint velocities), $\ddot q$ the accelerations.
  • Units are SI: metres, radians, seconds, newtons, newton-metres (Nm). 1 mrad = 0.001 rad; 1 µrad = 10−6 rad. At the Panda's reach (~0.8 m), 1 mrad of joint error moves the hand by at most roughly 1 mm.
  • File paths are relative to the repository root, e.g. planning/collision.py. Line numbers refer to commit 5dbeffd and are given where practical (Appendix C).
  • "The plant" means the simulated robot (the MuJoCo model that is stepped). "The model" in a controller means the controller's own copy of the dynamics, which can deliberately differ from the plant in mismatch experiments.

Part I — Understanding the ProjectWhat Robotics Lab is, what is in the repository, and what actually happens, line by line, when you run it.

Chapter 1What is Robotics Lab?

A first look: the robot, the simulator, the problems the project tries to solve, and the vocabulary used in the rest of the guide.

1.1 Why this project exists

Robotics Lab is a simulation platform for a robot arm. It contains no hardware and no real robot. A computer model of a seven-joint industrial research arm, the Franka Emika Panda, is simulated by the physics engine MuJoCo, and our Python code decides what torques the arm's motors apply at every instant. The goal is to build, piece by piece and with measured evidence, the software stack a real autonomous manipulator needs:

  1. Move accurately. Given a desired joint trajectory, make the simulated arm follow it with small error while respecting motor torque limits and joint speed limits (control).
  2. Move to places, not just joint angles. Given a desired hand position in space, find joint angles that put the hand there (inverse kinematics).
  3. Avoid obstacles. When the obvious motion would hit something, find a different collision-free route with a safety margin (motion planning and collision checking).
  4. Be honest about it. Measure every claim with reproducible experiments and automated tests, and record failures and limitations alongside successes.

The fourth point shapes the whole repository. Most of its 7,000 lines of project Python are the controller, planner and simulation code. A large share, however, consists of benchmarks, audit tools and 189 automated tests, and every milestone has a written research report in docs/research/.

Simulation comes first because it is cheap, repeatable and safe. A controller bug that drives a real Panda into a table can damage an expensive robot; in MuJoCo it just produces a number in a CSV file. Simulation also gives perfect measurements (the exact joint angles, the exact distance to an obstacle), which makes it possible to test whether an algorithm is correct before asking whether it is robust to sensor noise. The price is the reality gap: anything learned in simulation needs to be checked again on hardware. This project has not crossed that gap (Chapter 17).

1.2 The robot: a Franka Emika Panda

The Panda is a collaborative robot arm widely used in research labs. It has seven revolute (rotating) joints in a chain from the base to the hand, plus a two-finger parallel gripper. Seven joints give it one more degree of freedom than the six needed to place a hand at an arbitrary position and orientation in 3-D space, so it is redundant: the same hand position can be reached with a whole family of arm postures (elbow up, elbow down and everything between).

Verified in source code

The arm model is a verbatim copy of Google DeepMind's MuJoCo Menagerie Panda (robots/models/franka_emika_panda/, commit d7b481b recorded in SOURCE.txt). It is never edited; every change (torque motors, an end-effector site) is made in code by robots/panda.py. The arm's total mass in the model is 17.45 kg. Joint limits come from the XML; speed, acceleration and jerk limits from the Franka datasheet are constants in robots/panda.py (VELOCITY_LIMITS = 2.175 rad/s for joints 1–4 and 2.61 rad/s for joints 5–7). The motor torque limits are 87 Nm (joints 1–4) and 12 Nm (joints 5–7).

The Menagerie model ships with position servos: you command a desired joint angle and a stiff spring-damper inside the simulator pulls the joint there. In v0.3 the project added a torque-motor variant in which our code commands the joint torques directly, which is how modern research controllers are usually written. Both variants exist side by side (Panda(actuation="position") or "torque"), and the choice of controller selects the variant automatically (Chapter 3).

1.3 The environment and the physics engine

MuJoCo ("Multi-Joint dynamics with Contact") is an open-source physics engine designed for robotics and control research. Given the robot's current state (joint angles and velocities) and the motor commands, it computes how the state changes over one small time step, including gravity, inertia, joint friction-like damping, motor limits and contact forces when bodies touch. Calling it repeatedly advances simulated time. In this project one physics step is 2 ms (500 steps per simulated second), with MuJoCo's implicitfast integrator.

An environment is a MuJoCo scene file in environments/: a floor, usually a table, sometimes obstacles. The robot is attached at runtime to a site named robot_mount, so scene files know nothing about robots. There are five scenes: empty, table, obstacles (a box and a cylinder on the table), planning_demo (a wall across the table) and planning_narrow (the wall plus a ceiling, leaving a 34 cm gap).

1.4 What the software currently does

As of v0.5.2 the software can, entirely in simulation:

  • drive the arm through a list of joint-angle waypoints, or to a list of hand positions, with four interchangeable controllers: a PID outer loop on the position servos, a servo-setpoint model predictive controller (MPC), computed-torque control (CTC) and a torque-level MPC;
  • generate smooth joint trajectories whose timing is automatically stretched until they respect the velocity, acceleration, jerk and torque limits;
  • estimate unknown disturbance torques (pushes, wrong masses) and compensate them;
  • plan collision-free motions around known obstacles with a sampling-based planner (RRT-Connect), keeping 20 mm of clearance at every checked configuration, and shorten the resulting paths;
  • replan when the obstacle geometry is different at the start of an episode;
  • measure all of this in benchmarks that report tracking error, constraint violations, contacts, clearances and solver timing.

It does not perceive the world (no cameras), does not replan during motion, does not grasp objects, has no learning component, and has never controlled a real robot. Chapter 17 gives a precise capability matrix.

1.5 Simulation, planning, control, perception, learning

These five words are used loosely in everyday speech; in robotics they name distinct layers with different inputs, outputs and time scales. Keeping them apart is the single most useful habit for understanding this project.

Table 1.1. The layers of a robot software stack and where each stands in Robotics Lab.
LayerQuestion it answersTypical rateIn this project
SimulationGiven motor commands, how does the world move?500 Hz here (2 ms)MuJoCo, wrapped by simulation/engine.py. Replaces the real world.
PerceptionWhat is around the robot, and where?10–60 Hz (cameras)Absent. Obstacle geometry is read from the scene file: the planner is given the truth.
PlanningWhich route through space reaches the goal without collision?once per task hereplanning/: IK postures, RRT-Connect, shortcutting, collision checking. Runs once before motion starts.
Trajectory generationHow fast should the robot move along that route?once per tasktasks/trajectory.py: time-scaled minimum-jerk or double-S profiles.
ControlWhich motor commands make the arm follow the trajectory now?50–500 Hzcontrollers/: PID, servo MPC, CTC, torque MPC.
LearningHow can behaviour improve from data?offlineAbsent. No trained model anywhere in the code.

A frequent confusion is to expect the controller to avoid obstacles. In this design it cannot: the controllers receive only a joint reference and the measured joint state, and know nothing about walls. Obstacle avoidance happens before motion, in the planner, and the controllers keep the arm on the planned route. Chapter 9 explains why closed-loop MPC alone does not give obstacle avoidance.

1.6 What is autonomous and what is predefined

"Autonomous" means that the robot itself chooses actions to achieve a goal. Here is what the robot decides and what a human decided in advance:

Table 1.2. Decisions made by the software versus decisions fixed by a person.
Decided by the software at run timeFixed in advance by a person
Joint angles that reach a requested hand position (IK, with several candidate postures)The goal positions or joint waypoints themselves (YAML config)
A collision-free route around known obstacles (random-sampling planner)The obstacle geometry (scene files, optional overrides)
The duration of each motion segment, to respect limitsThe limits and safety fractions (YAML)
Every motor torque, 50–500 times per second, from measured stateController type, gains, weights, horizons (YAML)
Rejecting an unreachable or blocked goal, with a reasonWhat to do next after a rejection (nothing: the target is skipped)

So the robot is autonomous at the level of motion (how to get there safely) but not at the level of tasks (what to do and why). There is no perception, no task planner and no decision-making beyond "reach the listed targets in order".

1.7 The long-term vision

The project's own documents state the direction: next pick-and-place, then reinforcement learning and other learning methods (CLAUDE.md, "Planned next: pick-and-place. RL and learning come later"). The pieces built so far (accurate torque control, feasibility-aware trajectories, collision-aware planning with clearance, and a careful evaluation harness) are the foundation such work needs. Chapters 18–20 discuss what would have to be added: perception, world models, reactive replanning, grasping, and how learned components could plug into the existing interfaces.

2.7 tasks/

A task turns a description of the goal into a reference: a function of time returning a Reference(q, qd, waypoint_index, qdd). Tasks never touch the simulation.

  • JointTargetTask (joint_target.py): moves along straight joint-space lines between waypoints, each move timed by plan_segment and followed by a hold. Optional per-move durations (move_times, hold_times) support planned via points. Can loop.
  • trajectory.py: the timing laws (quintic, DoubleS), KinematicLimits, plan_segment (lengthens a move until velocity, acceleration, jerk and torque limits hold, or raises TrajectoryInfeasible) and check_reference.
  • CartesianReachTask (reach.py): resolves each (x, y, z) target through an injected plan function (either IK + straight-path check, or the motion planner), skips unreachable targets with a reason, and builds an internal JointTargetTask.
  • PlannedJointTask (planned_joint.py): like JointTargetTask but each move follows a planned path; raises PlanningFailed if any move cannot be planned.

2.8 planning/

  • CollisionChecker (collision.py): is a configuration valid (inside joint limits minus 0.05 rad, no contact, ≥ 20 mm from the environment)?   • shortcut, prune (shortcut.py): shorten a valid path while keeping it valid.
  • ik_candidates (ik.py): many IK solutions from different seeds, filtered by the checker, sorted by distance from the start.

3.1 Program start-up

main() (main.py, line 23) defines the command-line options with argparse: --config, --environment, --headless, --duration, --controller {pid, mpc, ctc, torque_mpc}, --control-rate, repeatable --target X Y Z, --planning/--no-planning, --plan-seed and --unchecked-direct. Importing main.py already imports the runner, which imports every controller, task and planner module, and MuJoCo itself (a compiled C library with Python bindings).

3.2 Configuration loading

load_config(path) (simulation/runner.py, line 76) reads the YAML file. configs/planning_demo.yaml starts with extends: default.yaml, so the default file is loaded first and the demo file is merged over it recursively (_merge), with one special rule: the task section is replaced as a whole, not merged. The merged configuration contains environment: planning_demo, a cartesian_reach task with a start configuration and two targets, a planning section (clearance 0.02 m, RRT budgets, IK seeding, exact_box_box: true), controller.type: torque_mpc and, inherited from the default, all the torque-MPC weights and the disturbance-observer settings. Command-line options then overwrite entries of this dictionary (lines 55–88 of main.py): for example --controller ctc sets config["controller"]["type"] = "torque_ctc", and --no-planning sets task.planning.enabled = False.

3.3 Robot model loading

SimulationRunner.__init__ (runner line 224) first decides which actuator model the controller needs: CONTROLLER_ACTUATION["torque_mpc"] = "torque". It constructs Panda(actuation="torque") and passes it to the engine. Inside build_spec (simulation/engine.py, line 53) the robot description loads the Menagerie XML as an MjSpec (Panda.load_spec), adds the ee_site, and converts actuators 1–7 to torque motors: gain 1, no bias (so the applied torque equals the command), command range equal to the force range (±87 Nm, ±12 Nm), and the home keyframe's commands set to zero (they were joint angles, which would otherwise be interpreted as torques).

3.4 Environment initialization

Still in build_spec, the environment file environments/planning_demo.xml is loaded into its own spec; geometry overrides would be applied here (none in this run); the robot's base body is attached to a frame at the robot_mount site (0, 0, 0.40), i.e. on the table top; and a contact exclusion between link0 and table is added because the base rests on the table. spec.compile() produces the MjModel (nq = 9 position coordinates: 7 arm joints and 2 finger slides; nu = 8 actuators), and MjData holds the changing state. The engine caches index arrays and limits and calls reset(), which loads the home keyframe and runs mj_forward so every derived quantity (link poses, contacts) is consistent. The scene contains the floor, the table (top and four legs) and the wall, a box 0.55 × 0.04 × 0.26 m.

3.5 Task creation

_build_task (runner line 291) sees type: cartesian_reach with planning enabled. It builds an ArmKinematics object (IK with joint-limit margin 0.05 rad and damping 0.05), then the motion planner through MotionPlanner.from_engine, which creates a CollisionChecker on a deep copy of the compiled model (Chapter 11). It then constructs CartesianReachTask(targets, start, plan=planner.plan_to_position, …). The task's constructor (tasks/reach.py, line 41) immediately calls plan(target, q_from) for each target in order, starting from the configured start configuration [0.246, 0.621, 0.211, −1.791, 0.089, 1.756, −0.785], which puts the hand at (0.45, 0.25, 0.50) m on the left of the wall. So planning happens during object construction, before the simulation starts.

3.6 Inverse kinematics

plan_to_position (planning/motion_planner.py, line 129) first checks that the start configuration is valid, then calls ik_candidates (planning/ik.py). That function runs damped-least-squares IK (ArmKinematics.solve_ik) from 22 seeds: the current configuration, the rest posture, 8 random perturbations of the current configuration (σ = 0.5 rad) and 12 uniformly random configurations. Each converged solution (position error below 0.1 mm) is checked by the collision checker; valid ones are sorted by weighted joint distance from the start, near-duplicates are merged, and at most 4 are kept. Chapter 4 explains the IK mathematics.

3.7 Motion planning

For the first IK candidate the planner calls RRTConnect.plan(q_from, q_goal, seed) (planning/rrt_connect.py, line 146). It first checks the straight joint-space edge: here it is blocked (the hand would sweep through the wall), which is what the output means by "direct edge BLOCKED". The two random trees then grow until they connect (21 nodes for the first target, 3,910 collision checks including IK validation and shortcutting), the path is reconstructed, and shortcut shortens it from 4.39 rad of joint motion to 1.41 rad with 4 vertices (start, two via points, goal). Each query gets a deterministic seed: 0 for the first target and 1000 for the second (_next_seed). The returned MotionPlan carries the path, the raw path and statistics. If planning had failed, the target would be marked rejected with the reason and skipped; the straight move is never substituted.

3.8 Trajectory generation

Back in CartesianReachTask, the path's interior vertices become via points: waypoints with zero hold time. The goal gets a 1.5 s hold. The task then builds one internal JointTargetTask with per-move durations: each planned edge requests segment_time = 1.0 s. For every edge, plan_segment (tasks/trajectory.py, line 189) computes the minimum-jerk timing along the straight joint line and lengthens it if 90% of the velocity limit, 50% of the acceleration limit, 5% of the jerk limit or 80% of the torque limit (checked with inverse dynamics of the controller's model at 101 samples) would be exceeded. The reference therefore stops at each via point and moves along exactly the edges the collision checker validated. The total duration of this run is 9.0 s (2 × 3 edges of ≥ 1 s plus 2 × 1.5 s holds).

3.9 Controller initialization

build_controller → build_torque_mpc (runner line 163) creates:

  • a MuJoCoPredictionModel on the controller's model with substeps = 10 (50 Hz control on a 500 Hz simulation, checked by control_substeps);
  • a ComputedTorqueController as fallback (plain CTC, no observer);
  • a JointDisturbanceObserver with time constant 10 ms (enabled in default.yaml);
  • the TorqueMPCController with horizon 25, the weights from the config and the reference_preview callable that lets the MPC ask the task for the reference at future times.

The controller's constructor builds the sparsity pattern of the quadratic program once (_build_structure), so later updates only overwrite numbers. Finally runner.reset() puts the robot at the task's first waypoint (the start configuration), opens the gripper (command 255) and places the red target marker.

3.10 Repeated control optimization

run_headless(9.0, before_step=count_contacts) loops 4,500 times. Each iteration calls SimulationRunner.step() (runner line 358), which asks the task for the reference at the current simulated time and calls controller.compute(q, qd, ref.q, ref.qd, dt, t, qdd_ref). Inside TorqueMPCController.compute (controllers/torque_mpc.py, line 264):

  1. the observer folds in the newest measurement and updates its disturbance estimate (every step);
  2. on every 10th call, _update linearizes MuJoCo around the measured state, writes the new model and references into the QP, warm-starts OSQP with the previous solution shifted by one interval, and solves; the first torque of the solution becomes the held command;
  3. between updates the held torque is returned, corrected by the change in the disturbance estimate since the last update (feedthrough).

In this run there were 450 updates (9 s × 50 Hz), all solved, with a mean of 37.7 OSQP iterations and a mean update time of 4.86 ms against a 20 ms budget. Chapter 8 dissects _update.

3.11 Applying motor commands

engine.set_arm_command(tau) clips the seven torques to the actuator command range and writes them into data.ctrl. With torque motors, the force MuJoCo applies equals this command. The gripper command (255, open) stays constant; nothing in this task closes it.

3.12 Physics simulation

engine.step() calls mujoco.mj_step, which computes the forward dynamics (inertia, Coriolis and gravity forces, joint damping, armature, actuator forces, contact forces if anything touches) and integrates 2 ms forward with the implicitfast integrator (Chapter 5). This is the only way the robot moves: the project rule "never set qpos/qvel to produce motion" is enforced by tests (test_arm_moves_only_through_actuators).

3.13 Feedback measurements

At the next iteration engine.arm_qpos() and arm_qvel() copy the joint angles and velocities out of MjData. These are the controller's measurements; the loop is closed because the next command depends on them. They are perfect (no noise) unless the configuration has a sensor_noise section, in which case the runner adds seeded Gaussian noise to what the controller sees, while metrics still use the true state.

3.14 Task completion

Nothing "finishes" in the control loop: the task simply returns the final waypoint with zero velocity after its last segment (for non-looping tasks), and the loop stops after duration simulated seconds (by default the task's duration, 9.0 s). There is no success detection inside the loop; success is judged afterwards from the log. If a target had been rejected, it would never have entered the reference.

3.15 Logging and evaluation

run_headless appends a sample to a RunLog every 10 steps (time, q, q_ref, the end-effector position, velocities, the reference acceleration, commands and applied actuator forces), giving 450 samples. main.py then prints the maximum joint tracking error over the log (rounded to 4 decimals, it shows 0.0000 rad, i.e. below 0.05 mrad; the planning benchmark measured 31 µrad for torque MPC on this scene, docs/research/v0.5-results.md §8), the final configuration and end-effector position, the contact count collected by count_contacts every step, the end-effector error at the end of each hold, and the MPC statistics from controller.stats.summary().

Caution: what "deadline overruns" means in simulation

The MPC counts an update as an overrun when its wall-clock time exceeds the 20 ms control period. In headless mode simulated time does not wait for wall-clock time, so an overrun has no effect on the motion: the simulator simply waits for the solver. In viewer mode the loop sleeps only when the simulation is ahead of the wall clock (_viewer_loop), so slow updates make the animation run slower than real time, but again do not change the physics. Overruns are therefore a warning about real-time feasibility on hardware, not a failure in the simulation (Chapter 9).

Chapter 4Robot mechanics and kinematics

Kinematics is the geometry of motion without forces: given the joint angles, where is the hand? Given a desired hand position, which joint angles reach it? How do small joint motions move the hand?

4.1 Joints and degrees of freedom

Intuition. Your arm is a chain of rigid bones connected by joints. Each joint allows one kind of relative motion. A door hinge allows rotation about one axis: one degree of freedom (DOF). A drawer slide allows translation along one axis: also one DOF. A robot arm is a chain of such joints, and the number of independent joint motions is its number of DOF.

Why it matters. A rigid object in space has 6 DOF (3 for position, 3 for orientation). To place a tool anywhere with any orientation, an arm needs at least 6 joints. The Panda has 7 revolute (hinge) joints, so for any reachable hand pose there is (generically) a one-parameter family of arm configurations; if only the hand position is specified, as in our IK, the family has 7 − 3 = 4 dimensions. This redundancy is useful (the elbow can move away from an obstacle while the hand stays put) and is exploited by the planner's multiple IK postures (Chapter 10).

4.2 Coordinate frames and rotation matrices

Intuition. To say where something is, you need a reference: an origin and three perpendicular axes. Robotics attaches such a frame to the world and one to every link. The pose of a link is the position and orientation of its frame relative to its parent's frame.

Mathematics. Orientation is described by a rotation matrix $R \in \mathbb{R}^{3\times3}$ whose columns are the link frame's $x$, $y$, $z$ axes written in the parent frame. A rotation by angle $\theta$ about the $z$ axis is

\[ R_z(\theta) = \begin{bmatrix} \cos\theta & -\sin\theta & 0 \\ \sin\theta & \cos\theta & 0 \\ 0 & 0 & 1 \end{bmatrix}. \]

Rotation matrices are orthonormal: $R^T R = I$ and $\det R = 1$, so $R^{-1} = R^T$. A vector $p_B$ expressed in frame B is expressed in frame A as $p_A = R_{AB}\, p_B$. Composing rotations is matrix multiplication: $R_{AC} = R_{AB} R_{BC}$, and the order matters. MuJoCo stores orientations internally as unit quaternions $(w, x, y, z)$ (four numbers, no singularities) and also provides rotation matrices (data.xmat, data.site_xmat).

The angle between two orientations $R_a$ and $R_b$ is the angle of the relative rotation $R_a^T R_b$. The project computes it in rotation_angle (simulation/kinematics.py, line 30) as $2\,\mathrm{atan2}(\|v\|, |w|)$ from the quaternion $(w, v)$ of $R_a^T R_b$, which is numerically accurate near 0 and π where the textbook formula $\arccos\big((\mathrm{tr}(R_a^TR_b)-1)/2\big)$ loses precision. It is used for the orientation metrics of the benchmark (v0.4).

4.3 Homogeneous transformations

A pose has a rotation and a translation. The homogeneous transformation packs both into one 4×4 matrix so that composing poses becomes a single multiplication:

\[ T_{AB} = \begin{bmatrix} R_{AB} & p_{AB} \\ 0\;0\;0 & 1 \end{bmatrix}, \qquad \begin{bmatrix} p_A \\ 1 \end{bmatrix} = T_{AB} \begin{bmatrix} p_B \\ 1 \end{bmatrix}, \qquad T_{AC} = T_{AB} T_{BC}. \]

Here $p_{AB}$ is the position of B's origin in A. For a revolute joint with angle $q_i$ about the link's local $z$ axis, the transform from link $i-1$ to link $i$ is a fixed offset (how the links are bolted together) followed by the joint rotation: $T_{i-1,i}(q_i) = T^{\text{fixed}}_{i}\; \mathrm{Rot}_z(q_i)$.

4.4 Forward kinematics

Intuition. Forward kinematics (FK) answers: if I set the joints to $q$, where is the hand? Walk down the chain from the base, applying each link's fixed offset and joint rotation in turn.

\[ T_{0,\text{EE}}(q) = T^{\text{fixed}}_1 R_z(q_1)\; T^{\text{fixed}}_2 R_z(q_2)\cdots T^{\text{fixed}}_7 R_z(q_7)\; T_{7,\text{EE}}. \]

A planar example. Two links of lengths $L_1$, $L_2$ moving in a plane with angles $\theta_1$ (from the $x$ axis) and $\theta_2$ (relative to link 1):

\[ x = L_1\cos\theta_1 + L_2\cos(\theta_1+\theta_2), \qquad y = L_1\sin\theta_1 + L_2\sin(\theta_1+\theta_2). \]

The map from angles to position is nonlinear (sines and cosines) but easy to evaluate.

In our code. We never write these matrices out by hand. MuJoCo's mj_kinematics walks the body tree defined in the XML and computes every body, geom and site pose. ArmKinematics.fk(q) (simulation/kinematics.py, line 79) copies the live state into a private MjData, overwrites the seven arm joints with $q$, calls mj_kinematics, and returns the position of ee_site; fk_pose also returns its rotation matrix. The engine has an equivalent forward_kinematics. Because they use scratch data, FK never disturbs the running simulation. At the home configuration $q = (0, 0, 0, -\pi/2, 0, \pi/2, -\pi/4)$ the end-effector site is at (0.554, 0, 0.921) m in the world (computed for this guide).

4.5 Jacobians

Intuition. If I nudge the joints by small amounts $\delta q$, how does the hand move? For small motions the answer is linear: $\delta x \approx J(q)\,\delta q$. The matrix $J$ is the Jacobian; its column $j$ is the hand velocity produced by moving joint $j$ alone at 1 rad/s.

Mathematics. Differentiate FK with respect to time: $\dot x = \frac{\partial x}{\partial q}\dot q = J(q)\dot q$. For the planar arm,

\[ J = \begin{bmatrix} -L_1 \sin\theta_1 - L_2\sin(\theta_1+\theta_2) & -L_2 \sin(\theta_1+\theta_2) \\ \phantom{-}L_1 \cos\theta_1 + L_2\cos(\theta_1+\theta_2) & \phantom{-}L_2\cos(\theta_1+\theta_2) \end{bmatrix}. \]

For a revolute joint $j$ with unit axis $a_j$ through point $o_j$, the geometric rule is: column $j$ of the position Jacobian is $a_j \times (p_{\text{EE}} - o_j)$. Its length is at most the distance from the joint axis to the hand. The same cross-product bound reappears in Chapter 11, where it limits how far any point of the robot can move between collision checks.

The Jacobian also maps forces: a force $F$ at the hand requires joint torques $\tau = J^T F$ (by the principle of virtual work, since power $F\cdot\dot x = F^T J \dot q = \tau^T\dot q$). This is how the disturbance experiments' 30 N push at the hand turns into joint torques.

In our code. ArmKinematics.jacobian(q) calls MuJoCo's mj_jacSite for the end-effector site and keeps the 3×7 positional block for the arm joints. test_fk_matches_engine_and_jacobian_matches_finite_differences checks it against finite differences of FK.

4.6 Inverse kinematics

Intuition. Inverse kinematics (IK) answers the reverse question: which joint angles put the hand at a desired position $x^*$? There is no general closed-form answer for the Panda, there may be no solution (target too far) or infinitely many (redundancy). The standard approach is iterative: start somewhere, measure the error $e = x^* - \mathrm{FK}(q)$, take a joint step that reduces it, repeat.

Mathematics: damped least squares. We want $\delta q$ with $J\delta q \approx e$. With 7 unknowns and 3 equations there are many solutions; the minimum-norm one is $\delta q = J^+ e$ with the pseudoinverse $J^+ = J^T(JJ^T)^{-1}$. Near singular configurations $JJ^T$ is nearly singular and the step explodes. Damped least squares (DLS) instead minimizes $\|J\delta q - e\|^2 + \lambda^2\|\delta q\|^2$, whose solution is

\[ \delta q = J^T (J J^T + \lambda^2 I)^{-1} e. \]

The damping $\lambda$ trades accuracy for robustness: steps stay bounded even at singularities. Because the arm is redundant, any joint motion in the null space of $J$ (motions that do not move the hand) can be added freely. Our solver uses it to pull the posture towards a rest configuration $q_{\text{rest}}$:

\[ \delta q \mathrel{+}= k_{\text{null}}\,(I - J^+J)(q_{\text{rest}} - q). \]

Each step is limited to 0.2 rad per joint and $q$ is clamped to the joint limits minus a margin.

Verified in source code

ArmKinematics.solve_ik(target, seed, tol=1e-4, max_iter=300, rest=None) (simulation/kinematics.py, lines 118–141) implements exactly the two equations above with $\lambda$ = 0.05 (config ik.damping), $k_{\text{null}}$ = 0.1, step limit 0.2 rad, joint-limit margin 0.05 rad, and converges when the position error is below 0.1 mm (configurable ik.tolerance). Orientation is left free. It returns an IKResult(q, success, error, iterations, reason). plan_target (v0.3) tries the current configuration and then the rest posture as seeds and checks collisions; planning/ik.py (v0.5) tries 22 seeds and keeps several valid postures; for perturbed and random seeds it passes rest=seed so the null-space term does not drag every solution to the same posture.

Example from our project. In configs/reach.yaml, the target out_of_reach at (1.30, 0, 0.60) m is about 1.3 m from the base; IK cannot converge and the task reports "IK did not converge (closest 360.6 mm)". The target inside_table at z = 0.38 m converges but is rejected by the collision check at the goal.

4.7 Joint-space versus Cartesian-space motion

A motion can be straight in joint space (every joint moves linearly from start to goal, all arriving together) or straight in Cartesian space (the hand moves along a line). They are different. A straight line in joint space generally produces a curved hand path, because FK is nonlinear. All motions in this project are straight in joint space: tasks/trajectory.py defines each move as $q(t) = q_a + (q_b - q_a)\,s(t)$. This choice has three advantages: joint limits are respected automatically (the joint-limit box is convex, so a line between two points inside it stays inside), timing limits per joint are easy to apply, and collision checking can bound the motion of every robot point (Chapter 11). The cost is that the hand path is not a straight line; the planned paths drawn in the viewer (planning/visualization.py, ee_polyline) show these curves.

4.8 Singularities and workspace limits

A configuration is singular when $J$ loses rank: some hand direction cannot be produced at all (for example when the arm is fully stretched, it cannot move the hand further outwards). Near a singularity small hand motions need very large joint velocities. The singular values of $J$ measure how close the arm is: the smallest one is the hand speed (m/s) achievable per rad/s of joint speed in the worst direction. Computed for this guide with ArmKinematics.jacobian: at home the singular values are 0.81, 0.73 and 0.31 m/rad; at the wall demo's start 0.78, 0.73 and 0.30 m/rad, so both are comfortably non-singular.

The workspace is the set of reachable hand positions. For the Panda it is roughly a sphere of radius about 0.85 m around the shoulder, minus regions excluded by joint limits and self-collision. Reachability is not checked analytically anywhere in the code; a target is unreachable when IK fails from all seeds.

Limitations
  • IK is position-only: the hand's orientation is whatever the solver ends at (the benchmark reports the hand turning by up to 49° in the reach scenario, docs/research/v0.4-results.md §6). Grasping would need orientation control.
  • IK failure from all seeds does not prove a target is unreachable; it is a numerical search.
  • There is no Cartesian-space motion (straight-line hand paths) and no velocity-level Cartesian control.

Chapter 5Robot dynamics and MuJoCo

Kinematics says where the robot is; dynamics says how torques make it move. This chapter derives the standard equation of motion of a robot arm and shows exactly how MuJoCo and our code represent each of its terms.

5.1 Generalized coordinates, velocities and accelerations

A rigid-body system is described by the smallest set of numbers that fixes every body's pose: its generalized coordinates. For an arm with revolute joints these are simply the joint angles $q$. Their derivatives $\dot q$ (rad/s) and $\ddot q$ (rad/s²) are the generalized velocities and accelerations. The pair $x = (q, \dot q)$ is the state: knowing it, and the torques applied from now on, determines the future motion.

Verified in source code

In MuJoCo the coordinates live in data.qpos (length nq = 9: seven arm joints, two finger slides) and the velocities in data.qvel (length nv = 9). For free bodies nq ≠ nv (quaternions), which is why the engine caches two different index arrays, arm_qpos_adr and arm_dof_adr (simulation/engine.py, lines 84–89). The controllers' state is the 14-vector $x = [q_{1..7}, \dot q_{1..7}]$ (controllers/prediction.py).

5.2 From one pendulum to the robot equation

A single joint. Take one link of mass $m$ whose centre of mass is a distance $l$ from a horizontal joint axis, with moment of inertia $I$ about the axis. With $\theta$ measured from the downward vertical, Newton's law for rotation (sum of torques = inertia × angular acceleration) gives

\[ I\ddot\theta + m g l \sin\theta = \tau, \]

where $\tau$ is the motor torque and $mgl\sin\theta$ is gravity's torque. Holding the link still at angle $\theta$ requires $\tau = mgl\sin\theta$: the gravity compensation torque.

Many joints: the Lagrangian route. For a chain, writing Newton's law for every body and eliminating the joint reaction forces is tedious. Lagrange's method is systematic. Define the kinetic energy $T(q,\dot q) = \tfrac12 \dot q^T M(q)\dot q$ (the inertia "seen" by the joints depends on the posture) and the potential energy $V(q)$ (gravity). The Euler–Lagrange equations $\frac{d}{dt}\frac{\partial T}{\partial \dot q} - \frac{\partial T}{\partial q} + \frac{\partial V}{\partial q} = \tau$ work out to

\[ \boxed{\; M(q)\,\ddot q + C(q,\dot q)\,\dot q + g(q) = \tau + \tau_{\text{ext}} \;} \]

with the following terms:

  • $M(q)$, the 7×7 inertia (mass) matrix: symmetric and positive definite. Its diagonal entry $M_{jj}$ is the inertia joint $j$ feels; off-diagonal entries mean that accelerating one joint pushes on others.
  • $C(q,\dot q)\dot q$, the Coriolis and centrifugal torques: the terms of $\dot M\dot q - \tfrac12 \partial(\dot q^T M \dot q)/\partial q$, quadratic in velocity. They are the "fictitious" forces of rotating frames; at the speeds in this project they are small compared with gravity and inertia.
  • $g(q) = \partial V/\partial q$, the gravity torques.
  • $\tau$, the actuator torques we command; $\tau_{\text{ext}} = J^T F$, joint torques produced by external forces $F$ (a push, a payload, contact).

Two more terms appear in a real joint and in MuJoCo: joint damping $-b\dot q$ (viscous friction) and armature $I_a$ (the reflected inertia of the motor rotor and gearbox, added to the diagonal of $M$).

5.3 How MuJoCo writes it

MuJoCo uses the same equation with its own names (MuJoCo documentation, "Computation"):

\[ M(q)\,\ddot q + c(q,\dot q) = \tau_{\text{act}} + \tau_{\text{passive}} + J_c^T f_c + \tau_{\text{applied}} \]

5.4 Actuators: position servos versus torque motors

An actuator maps a command to a joint torque. MuJoCo's general actuator computes $\tau = \text{gain}\cdot\text{ctrl} + \text{bias}(q,\dot q)$, then clips to the force range.

  • Position servo (Menagerie default): gain $k_p$, bias $-k_p q - k_d \dot q$, so $\tau = k_p(u - q) - k_d\dot q$, clipped. $k_p$ = 4500, 4500, 3500, 3500, 2000, 2000, 2000 Nm/rad and $k_d = 0.1\,k_p$ (panda.xml, lines 265–274). The command $u$ is an angle (rad), not a torque.
  • Torque motor (our v0.3 variant): gain 1, no bias, so $\tau = u$ in Nm, clipped to ±87/±12 Nm (Panda._make_torque_actuators).

The difference matters enormously for control. A servo is itself a stiff feedback loop running inside the physics at every step; a torque motor does exactly what it is told, so all feedback must come from our controller. Chapter 6 shows the consequences.

5.5 Numerical integration

The equation of motion gives $\ddot q$; the simulator must turn that into the next state. The simplest scheme, explicit Euler, is $\dot q_{k+1} = \dot q_k + h\ddot q_k$, $q_{k+1} = q_k + h\dot q_{k}$ with step $h$. It becomes unstable for stiff systems (large damping or stiffness relative to inertia) unless $h$ is tiny. Semi-implicit Euler updates velocity first and uses the new velocity for the position, which conserves energy much better. MuJoCo's implicitfast integrator goes further: it treats the velocity-dependent forces (damping, servo $k_d$) implicitly, solving $(M + hD)\,\dot q_{k+1} = M\dot q_k + h f(q_k, \dot q_k)$ where $D$ collects the derivative of the forces with respect to velocity. Heavily damped servos stay stable at $h$ = 2 ms.

Consequence used by the code

Because damping acts implicitly, the discrete-time step is not exactly the continuous equation sampled at 2 ms. Continuous-time inverse dynamics applied to measured finite-difference accelerations leaves a residual of about $h\,b\,\ddot q$ (≈ 0.02 Nm here) even with a perfect model. The disturbance observer therefore enables mjENBL_INVDISCRETE, MuJoCo's inverse dynamics of the discrete step, on a private model copy (controllers/disturbance.py, line 54). Likewise, at the servo force-clip boundary the implicit update changes form (damping leaves it while the force is clipped), so the one-step map is discontinuous there; controllers/prediction.py handles that with a force-unlimited backup model (Chapter 8).

5.6 Contact forces and friction

When two geoms touch, a real contact produces normal force (no interpenetration) and friction (resisting sliding). MuJoCo models contacts as soft constraints: for every contact it computes a signed distance dist (negative = penetration) and solves a convex optimization for contact forces that allows a tiny, controlled penetration (parameters solref, solimp). Contacts are only generated when geoms are closer than their margin (0 by default); the planner's collision checker exploits this by setting a 20 mm margin on obstacles in its private model copy (Chapter 11). Collision detection proceeds in phases: a broadphase that discards pairs whose bounding boxes do not overlap, a midphase using bounding-volume trees within multi-geom bodies, and a narrowphase that computes the actual contact for each geom pair with a routine chosen by the pair's shape types (box-box, mesh-box via a general convex algorithm, and so on). Two of the project's most important findings concern these phases (midphase, v0.5; box-box narrowphase, v0.5.1/v0.5.2).

In our experiments contact is never wanted: success requires zero robot contact steps. Contacts appear only in the deliberately unsafe baseline, where the arm drives into the wall (1,005–1,849 contact steps; Chapter 15).

Chapter 6Control theory fundamentals

How to compute motor commands that make the arm follow a reference: feedback, stability, PID, computed-torque control, disturbance observers, and the difference between position and torque control. Every controller in the repository is explained and compared.

6.1 Open loop, closed loop and feedback

Open-loop control computes commands from the goal alone, without looking at what the robot actually does: "apply this torque profile for 3 s". If the model is slightly wrong, or someone pushes the arm, the error grows unchecked. Closed-loop (feedback) control measures the actual state and corrects: the command depends on the tracking error $e = q_{\text{ref}} - q$. Every controller in Robotics Lab is closed-loop: compute() receives the measured $q$ and $\dot q$ at every 2 ms step.

6.2 Stability and the second-order error equation

A controller is stable if errors die out instead of growing. The workhorse model is the damped second-order system

\[ \ddot e + 2\zeta\omega_n \dot e + \omega_n^2 e = 0. \]

Its solutions behave like $e^{\lambda t}$ with $\lambda = -\zeta\omega_n \pm \omega_n\sqrt{\zeta^2 - 1}$. If both roots have negative real part the error decays. $\omega_n$ (rad/s) sets how fast the error decays and $\zeta$ sets how much it oscillates: $\zeta = 1$ ("critical damping") is the fastest decay without overshoot. The settling time to about 2% is roughly $4/(\zeta\omega_n)$. For discrete-time systems $x_{k+1} = A x_k$, the condition becomes: all eigenvalues of $A$ inside the unit circle, $|\lambda_i| < 1$.

Example from our model

The torque MPC's 20 ms prediction model, linearized at the home pose with the gravity-holding torque held constant, has a largest eigenvalue magnitude of 1.09 (computed for this guide). That is greater than 1, so holding a constant torque is open-loop unstable at that pose: any small deviation grows, as for a balanced pendulum. This is why the arm cannot be run open-loop and why the MPC must re-plan from fresh measurements.

6.3 PID control

Intuition. Push against the error (P), push harder if the error persists (I), and brake if the error is changing fast (D):

\[ u = K_p e + K_i \int_0^t e\,dt' + K_d \dot e. \]

P alone acts like a spring: it oscillates, and under a constant load such as gravity it leaves a steady error, since some error is needed to produce the holding force. D adds damping. I accumulates the remaining error until the holding force is supplied, at the cost of slower, possibly oscillatory transients and integrator windup if the actuator saturates. Figure 6.2 shows all four behaviours on a toy joint.

Verified in source code: JointPIDController (v0.1)

controllers/pid.py. It does not command torques. It shifts the setpoint of the Menagerie position servos, which are themselves PD controllers inside MuJoCo:

\[ u = q_{\text{ref}} + k_p e + k_i\!\int e\,dt + k_d(\dot q_{\text{ref}} - \dot q) + k_{\text{ff}}\,\dot q_{\text{ref}}, \]

with $k_p$ = 0.5, $k_i$ = 5.0, $k_d$ = 0, $k_{\text{ff}}$ = 0.1 (configs/default.yaml). The servo produces $\tau = k_{p,s}(u - q) - k_{d,s}\dot q$. Without the outer loop, gravity makes the servo sag about 0.008 rad. The integral term supplies the holding offset. The feedforward term $0.1\,\dot q_{\text{ref}}$ cancels the servo's damping lag, because for every Panda servo $k_{d,s}/k_{p,s} = 0.1$, so a joint moving at $\dot q_{\text{ref}}$ needs its setpoint $0.1\,\dot q_{\text{ref}}$ ahead. Anti-windup clamps the integral's contribution to 0.05 rad. Runs every 2 ms. Result (CLAUDE.md, tests): maximum tracking error below 4 mrad, steady-state error around 0.1 mrad.

6.4 Feedforward and feedback

Feedback reacts to errors after they appear; feedforward supplies the command the reference is known to need, before any error appears. If you know the motion will require 20 Nm to hold against gravity and 5 Nm to accelerate, apply 25 Nm directly and let feedback handle only what the model got wrong. Good controllers combine both. In the project: PID's $k_{\text{ff}}\dot q_{\text{ref}}$, CTC's inverse dynamics of $\ddot q_{\text{ref}}$, and MPC's reference preview (it sees the whole next 0.5 s of the reference) are all feedforward.

6.5 Computed-torque control

Intuition. If we know the robot's dynamics exactly, we can compute the torque that produces any desired acceleration, effectively cancelling gravity, inertia coupling and Coriolis forces. What remains is a simple double integrator per joint, which a PD law stabilizes.

Derivation. Choose the desired acceleration from the reference acceleration plus PD feedback, $\ddot q_{\text{des}} = \ddot q_{\text{ref}} + K_p e + K_d \dot e$, and the torque from inverse dynamics, $\tau = M(q)\ddot q_{\text{des}} + C(q,\dot q)\dot q + g(q)$. Substituting into the robot equation (with $\tau_{\text{ext}} = 0$) gives $M(\ddot q - \ddot q_{\text{des}}) = 0$, and since $M$ is invertible, $\ddot q = \ddot q_{\text{des}}$, i.e.

\[ \ddot e + K_d \dot e + K_p e = 0. \]

With $K_p = \omega_n^2$ and $K_d = 2\zeta\omega_n$ this is the standard second-order error equation: the gains directly set the error dynamics, identically for every posture.

Verified in source code: ComputedTorqueController (v0.3)

controllers/computed_torque.py. $\omega_n$ = 25 rad/s, $\zeta$ = 1, so $K_p$ = 625 s⁻², $K_d$ = 50 s⁻¹. The torque is ArmInverseDynamics.torque(q, qd, qdd_des), i.e. MuJoCo's mj_inverse, which includes armature and joint damping, clipped to the torque limits. Runs every 2 ms. It uses the controller's model (the plant itself unless mismatch is configured), so in nominal runs its model is perfect. It ignores velocity and joint limits: it follows any reference, feasible or not. v0.4 options: integral action $\ddot q_{\text{des}} \mathrel{+}= k_i\int e$ (error dynamics $\dddot e + K_d\ddot e + K_p\dot e + k_i e = 0$, stable by the Routh criterion only if $k_i < K_dK_p$ = 31,250, enforced by the constructor) and a disturbance observer ($\tau \leftarrow \tau - \hat d$). It is also the torque MPC's fallback.

6.6 Disturbance estimation

Intuition. A model-based controller is only as good as its model. Unknown forces, such as a push, a payload or masses that are 15% wrong, act like an unknown extra torque $d$. If the controller could measure $d$ it could cancel it. It cannot measure it directly, but it can infer it: compare the acceleration the robot actually showed with the acceleration the model predicted for the torque that was applied.

Mathematics. Model the plant as $M(q)\ddot q + h(q,\dot q) = \tau_{\text{applied}} + d$. Each physics step, using the discrete inverse dynamics ID:

\[ d_{\text{raw},k} = \mathrm{ID}\!\left(q_{k-1}, \dot q_{k-1}, \frac{\dot q_k - \dot q_{k-1}}{\Delta t}\right) - \tau_{\text{applied},k-1}, \qquad \hat d_k = \hat d_{k-1} + \frac{\Delta t}{T}\left(d_{\text{raw},k} - \hat d_{k-1}\right). \]

The second equation is a first-order low-pass filter with time constant $T$ that smooths the noisy raw estimate. Using the applied (post-clipping) torque means the estimate does not wind up when the motors saturate.

Verified in source code: JointDisturbanceObserver (v0.4)

controllers/disturbance.py: exactly the two equations above, with mjENBL_INVDISCRETE on a private model copy, $T$ = 10 ms, and $|\hat d|$ clipped to half the torque limit. The controller calls update(q, qd, dt) each step and applied(tau) after choosing its command. Off by default for CTC, on by default for the torque MPC, where it turns the MPC "offset-free" (Chapter 8).

Reported result (v0.4 report §5)

Under a 30 N sideways push on the hand for 1 s, maximum joint error: CTC 35.2 mrad → 3.14 mrad with the observer; torque MPC 12.1 → 3.62 mrad. With controller masses 25% too low: CTC 9.09 → 0.84 mrad; MPC 3.44 → 0.95 mrad. Observer time constant chosen from a noise/rejection trade-off. With sensor noise, step-to-step torque jitter for CTC was 0.21 Nm without observer, 0.45 Nm at T = 10 ms and 0.78 Nm at T = 5 ms (which rejected the push to 1.6 mrad).

Wording discrepancy: CLAUDE.md says a 5 ms observer "triples torque jitter". The report's table shows ×1.7 relative to the chosen 10 ms observer and ×3.7 relative to no observer; the numbers above are the report's.

6.7 Position control versus torque control

With position servos, a stiff PD loop (up to 4500 Nm/rad) inside the simulator holds each joint; our controller only moves the setpoints. This is robust against pushes (the servo resists immediately) and needs no model, but the controller has only indirect authority over torque. Each change of setpoint $\Delta u$ creates a torque spike $k_p\Delta u$ lasting about 1 ms, which is clipped at the 12 Nm wrist limit. With torque motors, the controller decides every Nm. It can respect torque limits exactly and exploit the dynamics, but it is responsible for everything, including holding the arm against gravity. If its model is wrong or it has no integral/observer action, it deflects under pushes.

Reported result (v0.3 report §8, finding 3)

Under the 30 N push, the servo controllers deflected 3.4 mrad (PID) and 2.0 mrad (servo MPC). The torque controllers without observer deflected 12 mrad (MPC) and 35 mrad (CTC). Stiff servos reject unmodelled pushes better than torque control without disturbance estimation.

Chapter 7MPC from first principles

Model predictive control chooses each command by solving an optimization problem about the future, again and again. This chapter builds the idea from scratch, works a small example by hand and by computer, and only then turns to the seven-joint robot.

7.1 What MPC is

Intuition. When you drive, you do not decide the steering angle only from where the car is now. You look ahead at the road for the next few seconds, imagine how the car will respond to steering and braking, choose a plan that keeps you on the road comfortably, start executing its first moment, and then, a fraction of a second later, look again and re-plan. That is model predictive control:

  1. measure the current state;
  2. use a model to predict how the system would evolve over a finite future window for any candidate sequence of commands;
  3. choose the command sequence that minimizes a cost (tracking error, effort, roughness) while respecting constraints (motor limits, speed limits);
  4. apply only the first command; discard the rest; repeat at the next sampling instant.

Why it matters. PID and computed-torque control react to the current error. MPC is the standard method that anticipates the reference and handles constraints explicitly: if the motor can deliver at most 12 Nm, the optimizer plans within that limit instead of discovering it when the torque is clipped. That is exactly what distinguishes the torque MPC from CTC in this project's results.

7.2 Why it is called model predictive control

Model: it needs an explicit mathematical model of the plant's dynamics. Predictive: it uses the model to predict future states over a horizon. Control: the output is the control input applied now. The family also goes by "receding-horizon control". In industry it has been used in chemical process control since the 1970s, where slow dynamics left minutes for each optimization; fast solvers have brought it to robots with millisecond sampling times.

7.3 Receding-horizon optimization

Re-planning at every step is what makes MPC a feedback controller: each new plan starts from the measured state, so model errors and disturbances are corrected at the next update. The plan itself is open-loop over the horizon; the closed loop comes from repetition. The horizon "recedes": it always extends the same length into the future from the current time.

7.4 Prediction models: continuous to discrete time

Physics gives a continuous-time model $\dot x = f(x, u)$. The controller only changes its command at sampling instants $t_k = kT_s$ and holds it constant in between (zero-order hold). It therefore needs the discrete-time map from one sampling instant to the next:

\[ x_{k+1} = F(x_k, u_k). \]

Example: one joint. A single joint with inertia $I$ and torque $\tau$ (no gravity, no friction) has state $x = (\theta, \omega)$ and $\dot\theta = \omega$, $\dot\omega = \tau/I$. With $\tau$ constant over an interval of length $T_s$, integrating exactly gives

\[ \theta_{k+1} = \theta_k + T_s\,\omega_k + \frac{T_s^2}{2I}\,\tau_k, \qquad \omega_{k+1} = \omega_k + \frac{T_s}{I}\,\tau_k, \qquad\text{i.e.}\quad x_{k+1} = \underbrace{\begin{bmatrix}1 & T_s\\ 0 & 1\end{bmatrix}}_{A} x_k + \underbrace{\begin{bmatrix} T_s^2/2I \\ T_s/I\end{bmatrix}}_{B} \tau_k. \]

This is a linear model, $x_{k+1} = Ax_k + Bu_k$. Real robots are nonlinear (gravity contains sines; inertia depends on posture). Linear MPC approximates the nonlinear map by a linear (affine) one around the current operating point, $x_{k+1} \approx Ax_k + Bu_k + c$, re-computed at every update. Nonlinear MPC keeps $F$ nonlinear and solves a harder non-convex problem. The project uses linear MPC (Chapter 8).

7.5 State and control vectors

The state $x_k$ must contain everything needed to predict the future given the inputs. For a rigid arm that is the joint positions and velocities: $x = (q, \dot q) \in \mathbb{R}^{14}$ for 7 joints. The control (input) $u_k$ is what the controller sets: $u = \tau \in \mathbb{R}^7$ for the torque MPC, or 7 servo setpoints for the servo MPC. Over a horizon of $N$ steps the unknowns are $u_0, \dots, u_{N-1}$, and with them the predicted states $x_1, \dots, x_N$.

7.6 Prediction and control horizons

The prediction horizon $N$ is how many steps ahead the model looks; $N T_s$ is the look-ahead time. Some formulations use a shorter control horizon $N_u < N$, after which the input is held constant, to reduce the number of unknowns. Our MPCs use $N_u = N$. Longer horizons see further (they can start a manoeuvre earlier) but cost more computation, and a linearized model becomes less accurate far into the future. The sampling time $T_s$ trades responsiveness against the time available to solve each problem.

Values in this project

Torque MPC: $T_s$ = 20 ms (50 Hz), $N$ = 25, look-ahead 0.5 s. Servo MPC: $T_s$ = 20 ms, $N$ = 15, 0.3 s (configs/default.yaml).

7.7 Objective (cost) functions

The cost turns "good behaviour" into a number. The most common form is a sum of weighted squares:

\[ J = \sum_{k=1}^{N} (x_k - r_k)^T Q\,(x_k - r_k) \;+\; \sum_{k=0}^{N-1} u_k^T R\,u_k \;+\; \sum_{k=0}^{N-1} (u_k - u_{k-1})^T S\,(u_k - u_{k-1}). \]

The first term penalizes deviation from the reference $r_k$ (position and velocity), the second penalizes effort, the third penalizes jerky changes of the command. The diagonal weight matrices $Q$, $R$, $S$ express priorities: large $Q$ means "track tightly"; large $R$ means "save torque". Squares are used because they make the problem a convex quadratic program (below) and punish large errors much more than small ones. Often the last stage gets a larger weight (a terminal weight) to stand in for the future beyond the horizon.

7.8 State and actuator constraints

Constraints are what MPC handles better than any classical controller:

  • Input constraints $u_{\min} \le u_k \le u_{\max}$ (motor torque limits). Physically absolute, so they are imposed as hard constraints.
  • State constraints $x_{\min} \le x_k \le x_{\max}$ (joint position and speed limits). If a disturbance has already pushed the state outside, a hard state constraint makes the problem infeasible (no solution exists), which is dangerous for a controller. They are therefore usually soft: add a slack variable $s_k \ge 0$, require $x_{\min} - s_k \le x_k \le x_{\max} + s_k$, and penalize $s$ heavily in the cost, $\rho_2\|s\|^2 + \rho_1\sum s$. With a large enough linear weight $\rho_1$ (an exact penalty), the slack stays exactly zero whenever the hard version is feasible.

7.9 Quadratic programming

Collect all unknowns in one vector $z = (x_1, \dots, x_N, u_0, \dots, u_{N-1}, s_1, \dots)$. The cost is quadratic in $z$ and every constraint, including the dynamics $x_{k+1} = Ax_k + Bu_k + c$, is linear. That is a quadratic program (QP) in the standard form used by the OSQP solver:

\[ \min_z \;\tfrac12 z^T P z + q^T z \qquad \text{subject to} \qquad l \le \mathcal{A} z \le u. \]

Equality constraints are rows with $l = u$. If $P$ is positive semidefinite the problem is convex: any local minimum is the global minimum, and reliable solvers find it in a bounded, predictable number of iterations. This is the decisive practical advantage of linear MPC over nonlinear MPC.

Two ways to set up the QP exist. The condensed form eliminates the states using the dynamics ($X = \Phi x_0 + \Gamma U$), leaving only the inputs: few variables, but dense matrices. The sparse (or simultaneous) form keeps the states as variables and the dynamics as equality constraints: more variables, but very sparse matrices that a sparse solver handles efficiently. Our MPCs use the sparse form; v0.3 measured a condensed variant and found it slower (94 ms per solve) because the matrices become dense.

OSQP (Operator Splitting Quadratic Program solver) solves such QPs with ADMM, an iterative method that alternates between a linear-system solve (with a factorized KKT matrix) and a simple projection onto the bounds. Its useful properties for MPC are that a warm start from the previous solution cuts iterations, an iteration limit bounds the solve time, and solution polishing refines the approximate ADMM solution to high accuracy when the active constraints have been identified. Its tolerances eps_abs/eps_rel define "converged".

7.10 A worked example: one joint, by hand and by computer

Take the single joint above with $I$ = 0.5 kg·m² and $T_s$ = 0.1 s:

\[ A = \begin{bmatrix}1 & 0.1 \\ 0 & 1\end{bmatrix}, \qquad B = \begin{bmatrix}0.01 \\ 0.2\end{bmatrix}. \]

Goal: move from rest at $\theta = 0$ to $\theta = 1$ rad and stop there, so $r = (1, 0)$. Weights: $Q = \mathrm{diag}(10, 1)$, $R = 0.1$, no rate term.

7.10.1 Horizon N = 1, by hand

With one step, $J(u_0) = (x_1 - r)^TQ(x_1 - r) + R u_0^2$ with $x_1 = Ax_0 + Bu_0$. Setting $dJ/du_0 = 0$:

\[ 2B^TQ(Ax_0 + Bu_0 - r) + 2Ru_0 = 0 \quad\Longrightarrow\quad u_0^* = \frac{B^TQ\,(r - Ax_0)}{B^TQB + R}. \]

From rest, $Ax_0 = 0$, $B^TQr = 0.01\cdot 10\cdot 1 = 0.1$, $B^TQB = 10\cdot 0.01^2 + 1\cdot 0.2^2 = 0.041$, so $u_0^* = 0.1/0.141 = $ 0.709 Nm. The predicted state is $x_1 = (0.0071, 0.142)$. The one-step controller is greedy: it does not "know" that velocity built up now must be braked later, except through the velocity weight.

7.10.2 Horizon N = 20 with a torque limit, by computer

Now look 2 s ahead ($N$ = 20) and add the hard constraint $|\tau| \le 1$ Nm. This has 60 unknowns (40 states, 20 torques), so we solve it as a QP with OSQP, exactly as the project's controllers do (docs/guide_src/make_figures.py, mpc_example).

Computed for this guide
  • Without the limit the optimal first torques are 6.43, 1.84, −0.30, −1.15, … Nm: a large kick, then braking. The first value is 6.4 times the motor's limit.
  • With the limit the optimal plan is: full torque +1.0 Nm for 6 steps (0.6 s), a partial step of 0.21 Nm, then braking (−0.71, −1.0, −1.0, −0.87, …) and a gradual approach. The predicted angle reaches 0.99 rad at the end of the horizon. This is the familiar "bang–coast–brake" shape, discovered by the optimizer rather than programmed.
  • In closed loop (re-solve every 0.1 s, apply the first torque) the joint reaches 0.78 rad at 1 s, 0.9945 rad at 2 s and 0.9999 rad at 3 s, never exceeding 1 Nm.

Notice what happened. Nothing in the controller says "accelerate, then brake". The plan emerges from three ingredients: the model (which says how torque changes the state), the cost (which says what we want), and the constraint (which says what is possible). The same three ingredients, in 14 state dimensions instead of 2, are what TorqueMPCController solves 50 times per second.

7.11 Why classical MPC needs no training

Nothing in MPC is learned from data. The model comes from physics (here, MuJoCo's equations evaluated at the current state); the cost and constraints are written by the engineer; the optimizer computes the answer from scratch at every step. There are no trainable parameters, no dataset and no training phase. Change the cost weights or the target and the very next solve reflects it. This is also why MPC needs an accurate model: it can only be as good as its predictions. (Learning can be combined with MPC, for example to learn a model or a terminal cost, but this project does not do so.)

7.13 What can go wrong: solver failure, instability, missed deadlines

  • Infeasibility. Hard constraints that cannot all be satisfied (for example a state already outside a hard limit) leave the QP without a solution. Remedy: soft state constraints, which our MPCs use by default.
  • Ill-conditioning. Weights or variables spanning many orders of magnitude make the solver slow or inaccurate. The torque MPC optimizes normalized torques $\tau/\tau_{\max}$ for exactly this reason (Chapter 8).
  • Iteration limit. If OSQP needs more than max_iter = 500 iterations, the solve fails; our controllers then hand over to a fallback controller (PID or CTC) until the next successful update.
  • Model error. The plan is optimal for the model. If the model is wrong (wrong masses, linearization error far along the horizon, unmodelled push), the closed loop can perform poorly or, with aggressive weights, even become unstable: the servo MPC went unstable with a position weight of 1e5 (README, "MPC design notes").
  • Deadlines. On a real robot the next command is needed every $T_s$. If linearization plus the solve take longer, the update is late. This project measures that (deadline overruns) but, being a simulation, does not suffer from it physically (Chapter 9).
  • Stability is not automatic. Finite-horizon MPC is not guaranteed stable in general; theory provides terminal costs and constraints that guarantee it. Our controllers use a terminal weight multiplier but no terminal constraint, and their stability is established empirically, not proven.

Chapter 8Our actual torque MPC implementation

A line-by-line account of TorqueMPCController (controllers/torque_mpc.py) and its prediction model (controllers/prediction.py). Every equation in this chapter corresponds to code; the source location is given under it.

8.1 Overview

The torque MPC is a linear, time-invariant-over-the-horizon, sparse-QP MPC with soft state constraints, hard torque limits, reference preview and an input-disturbance observer, re-linearized at every update from MuJoCo itself. At each update (every 10th physics step, i.e. 50 Hz) _update (line 295) performs:

  1. read the measured state $x_0 = (q, \dot q)$ and check it is finite;
  2. compute the gravity torque $\tau_g(q)$ and linearize MuJoCo around $(x_0, \tau_{\text{prev}})$: $A$, $B$, $c$;
  3. add the disturbance estimate to the model; form the references $r_1..r_N$ from the task preview;
  4. write the new numbers into the fixed-structure QP; warm-start OSQP; solve;
  5. keep the first torque as the held command; record statistics. On any failure, hand over to CTC.

8.2 State, control and decision vectors

Verified in source code
  • State: $x = (q_1..q_7, \dot q_1..\dot q_7) \in \mathbb{R}^{14}$ (self.nx = 2 * n, line 107). Fingers are not part of it.
  • Control: joint torques $\tau \in \mathbb{R}^7$ (Nm), held constant for $T_s$ = 20 ms (zero-order hold).
  • Decision variable for torques: the normalized torque $v_k = \tau_k / \tau_{\text{scale}}$ with $\tau_{\text{scale}} = (87, 87, 87, 87, 12, 12, 12)$ Nm, the largest absolute force limit per joint (line 114).
  • Full QP vector (comment at line 137): $z = [\,x_1, \dots, x_N \;|\; v_0, \dots, v_{N-1} \;|\; s_1, \dots, s_N\,]$, with one slack per state component per knot. For $N$ = 25: 350 + 175 + 350 = 875 variables.

Why normalize? The position weight is $10^5$ per rad² while an effort weight of 1 per (Nm)² on a 87 Nm joint is $1/87^2 \approx 1.3\times10^{-4}$ per raw Nm². The diagonal of $P$ would span about ten orders of magnitude. The v0.3 report measured the consequence: OSQP's polishing failed and the at-rest plan drifted 2.7 mrad. With normalized torques the drift is $10^{-9}$ rad (docstring lines 31–34; v0.3-results.md §6).

8.3 The prediction model

8.3.1 One physics step, differentiated by MuJoCo

MuJoCoPredictionModel.linearize(q, qd, u_lin) (prediction.py, line 245) uses the "power" method (_jacobians_power, line 270). It copies the live simulation state into private scratch data (positions, velocities, controls and the constraint solver's warm start; not the applied external forces, which a real controller cannot measure), overwrites the arm state and command, and calls mujoco.mjd_transitionFD, which returns the Jacobians of one complete 2 ms mj_step by forward finite differences with $\varepsilon = 10^{-6}$:

\[ A_1 = \frac{\partial x^{+}}{\partial x}\Big|_{x_0,\,u_{\text{lin}}}, \qquad B_1 = \frac{\partial x^{+}}{\partial u}\Big|_{x_0,\,u_{\text{lin}}} \quad (\text{arm block only, } 14\times14 \text{ and } 14\times7). \] prediction.py, _jacobians_power, lines 270–286

These are derivatives of MuJoCo's actual discrete step (implicitfast integration, armature, damping, the full rigid-body dynamics), not of a textbook ODE. Only the arm block is kept: the fingers rest on a joint limit, and finite differences across that limit once produced a spectral radius of $10^{22}$ when the full matrix was composed.

8.3.2 Composition over the control interval

Assuming the one-step Jacobians stay constant over the $n$ = 10 physics steps of one control interval, with the torque held constant:

\[ A = A_1^{\,n}, \qquad B = \left(A_1^{\,n-1} + A_1^{\,n-2} + \dots + A_1 + I\right) B_1 . \] prediction.py, lines 281–285 (loop: B_n = A1 B_n + B1; A_n = A1 A_n)

8.3.3 The affine term makes the model exact at the linearization point

A true 10-step MuJoCo rollout $f_n$ from $(x_0, u_{\text{lin}})$ is run, and

\[ c = f_n(x_0, u_{\text{lin}}) - A x_0 - B u_{\text{lin}} . \] prediction.py, linearize, lines 264–266

With this choice $x_1 = Ax_0 + Bu_{\text{lin}} + c$ equals the true MuJoCo state after one interval if the command is $u_{\text{lin}}$, so gravity, Coriolis and damping at the current state are included exactly, and only the change of command enters linearly. The linearization command is the last applied torque $\tau_{\text{prev}}$ (or $\tau_g$ before the first command; torque_mpc.py lines 305–307).

8.3.4 Safeguards

  • jacobians_plausible (line 124) rejects non-finite matrices, entries above $10^3$, or a spectral radius of $A$ above 2. If the true-model Jacobians fail, Jacobians of a copy with force limits removed (jac_model) are used; if those fail too, the update raises and the fallback takes over. The backup exists for the servo case, where the one-step map is discontinuous at the force-clip boundary.
  • The scratch data never writes the live MjData (test_prediction_never_modifies_live_state) and never sees xfrc_applied (test_external_forces_are_not_visible_to_the_model).

8.3.5 Offset-free model with the disturbance estimate

With the observer enabled (default), its current estimate $\hat d$ is treated as a constant known input over the whole horizon:

\[ x_{k+1} = A x_k + B\,(\tau_k + \hat d) + c \;=\; A x_k + B\tau_k + \underbrace{(c + B\hat d)}_{c'} . \] torque_mpc.py, _update, lines 311–313

The same $(A, B, c')$ is used for every stage $k = 0..N-1$: the model is linear time-invariant over the horizon. This is linear MPC, not nonlinear MPC.

The effort term penalizes torque beyond what is needed to hold the arm still, not torque itself: holding against gravity is free. The rate term smooths the torque sequence and, through $v_{-1}$, penalizes jumps relative to the torque currently applied. This is also why the torque MPC is more sensitive to position noise than CTC (v0.4 report §5).

8.7 How the reference reaches the controller

The controller never imports tasks. The runner passes a callable reference_preview(t) that returns the task's $(q_{\text{ref}}, \dot q_{\text{ref}})$ at any time $t$ (SimulationRunner._reference_preview). At each update, _references (line 284) evaluates it at $t + kT_s$ for $k = 1..N$, giving the 25 future reference states $r_k$; the task's reference acceleration is not used by the MPC. Without a preview function the controller would extrapolate the current reference linearly. The preview means the MPC "sees" corners of the trajectory 0.5 s before reaching them.

  2. if self._step % substeps == 0, run _update;
  3. output the held MPC torque, corrected by the change of the disturbance estimate since the last update:
\[ \tau(t) = \mathrm{clip}\!\left(\tau_{\text{MPC}} - \big(\hat d(t) - \hat d_{\text{update}}\big),\; \tau_{\min},\; \tau_{\max}\right) \] torque_mpc.py, compute, lines 275–278 (disturbance_feedthrough = true in default.yaml)

This 500 Hz inner correction matters: with a 10 ms observer but without feedthrough, the push error was 7.1 mrad instead of 3.75 mrad, because the torque is otherwise frozen for 20 ms (v0.4 report §5).

8.9 Failure handling

Any exception inside _update (non-finite state, implausible linearization, inconsistent QP data, solver status not accepted) sets _using_fallback = True and clears the warm start. Until the next successful update, compute returns the fallback's command: plain computed-torque control (no observer, no integral), built by build_ctc(..., fallback=True). The applied command is always recorded in _applied, and the next linearization and rate term are anchored to it. That design comes from the one implementation bug the project found in its MPC line: in v0.2 the servo MPC anchored to its own stale solution after a fallback, which cascaded into 275 fallbacks out of 450 updates; anchoring to the applied command reduced them to 43 (v0.3 report §2). In the traced demo run there were 0 fallbacks.

8.10 How the torque reaches MuJoCo

SimulationRunner.step passes the returned 7-vector to engine.set_arm_command, which clips it to ctrlrange (±87/±12 Nm) and writes data.ctrl; mj_step applies it through the torque-motor actuators (gain 1, no bias), so actuator_force equals the command (test_torque_command_is_applied_force). Note one idealization: the command computed from the state at time $t$ is applied at time $t$, although on hardware the 4–5 ms of computation would delay it.

9.3 The fast and wrist investigation: infeasible references

In v0.3 the torque MPC looked dramatically worse than CTC on the fast and wrist scenarios (169 and 532 mrad vs 0.54 and 0.29 mrad). CTC simply follows them and breaks the speed limit by 43%. The MPC obeys the limit and must fall behind.

The lower bound (v0.4 report §2)

For a quintic move the peak speed is $1.875|\Delta q|/T$. A follower limited to $v_{\max}$ must accumulate a lag of $L = \int(|\dot q_{\text{ref}}| - v_{\max})^+\,dt$ over the over-speed stretch: 294 mrad (fast) and 608 mrad (wrist). With perfect look-ahead it can run ahead by $L/2$ before and end up $L/2$ behind after, so no speed-limited controller can do better than ≈147 mrad (fast) or ≈304 mrad (wrist) maximum error. The MPC's 169 mrad is within 15% of the bound. Removing only the speed limit, it tracks to 0.10 / 0.04 mrad; on feasible timing to 0.02 / 0.01 mrad.

The lesson generalizes: a controller that enforces limits will appear to "fail" on an infeasible reference. Feasibility belongs in trajectory generation, which v0.4 added (Chapter 12). The historical scenarios were kept unchanged so v0.3 numbers stay comparable.

9.7 Is it really closed loop?

Yes. Every update starts from the measured state (x0 = np.concatenate([q, qd])), and the test test_torque_mpc_state_feedback checks that a perturbed state changes the command. Between updates the held torque is still corrected at 500 Hz by the observer feedthrough. What is open-loop is each individual plan over its 0.5 s horizon, as in every MPC.

9.8 Why closed-loop MPC does not give obstacle avoidance

A frequent misconception is that an MPC "plans" and should therefore avoid obstacles. Ours cannot, for three reasons: (1) it has no information about obstacles: its inputs are joint states and a joint reference; (2) its cost only measures distance from the reference, so any route that tracks well is "good"; (3) collision avoidance is a non-convex constraint (the robot must be outside every obstacle), which does not fit a convex QP without approximation, and the horizon of 0.5 s is far too short to discover a detour over a wall. In this project obstacle avoidance is the planner's job (Chapter 10); the MPC keeps the arm on the planned, collision-checked path. Chapter 19 discusses how obstacle constraints could be added to an MPC in the future.

9.9 Is it real-time on our laptop?

In the sense that an average update (≈5 ms) is shorter than the control period (20 ms): yes, with margin on a quiet machine. In the strict sense of guaranteed deadlines: no. The code runs in Python on Windows, a non-real-time operating system; worst-case update times of 16.6 ms were observed in the traced run, and up to 22 of 300 deadlines were missed under load. In simulation a missed deadline has no physical effect (the simulated clock waits, Chapter 3), so tracking results are unaffected; on hardware it would mean a late command. How much faster than real time a headless torque-MPC run is was not reported for the current version; the v0.2 README reported a real-time factor of about 4.5× for the 50 Hz servo MPC and about 30× for PID, and the benchmark records realtime_factor per run.

Chapter 10Robot motion planning

When the straight motion to a goal would hit something, the robot needs a different route. This chapter explains configuration space, why sampling-based planners are used for arms, how RRT-Connect works, and exactly how our planner is implemented.

10.1 Configuration space

Intuition. Planning for an arm is hard in the physical world because the arm is a large, oddly shaped, moving object. The trick is to change viewpoint: describe the robot by a single point, its configuration $q$, in the space of all joint-angle combinations, the configuration space or C-space. For the Panda arm, C-space is a 7-dimensional box (the joint limits). Every point in it is one complete arm posture.

Obstacles in C-space. A configuration is in collision if the arm at that posture overlaps an obstacle (or itself). The set of such configurations is the C-obstacle. A small box on the table becomes a large, curved region in C-space, because many joint combinations sweep some link through it. Planning becomes: find a continuous curve from $q_{\text{start}}$ to $q_{\text{goal}}$ that stays in the free part of C-space, $\mathcal{C}_{\text{free}}$.

The Panda's C-space has 7 dimensions, so we cannot draw it, and we never compute the C-obstacle explicitly. We only have a membership test: for any given $q$, the collision checker says whether it is free (Chapter 11).

10.2 Graph search versus sampling-based planning

The classical approach discretizes C-space into a grid and runs a graph search (Dijkstra, A*) from start to goal. It finds the shortest grid path if one exists, but the number of cells grows exponentially with dimension: 100 cells per joint gives $100^7 = 10^{14}$ cells for the Panda, far beyond any memory. This "curse of dimensionality" is why arm planners are sampling-based: they draw random configurations, keep the free ones, and connect nearby ones with checked straight edges, exploring the free space without ever representing it fully. Sampling-based planners are probabilistically complete: if a path exists, the probability of finding it approaches 1 as the number of samples grows, but a failure after a finite budget does not prove that no path exists.

10.3 Rapidly-exploring random trees

An RRT grows a tree from the start. Each iteration: draw a random configuration $q_{\text{rand}}$; find the tree node $q_{\text{near}}$ closest to it; take a step of length at most $\delta$ from $q_{\text{near}}$ towards $q_{\text{rand}}$, giving $q_{\text{new}}$; if $q_{\text{new}}$ and the edge to it are collision-free, add it to the tree. Because large unexplored regions are more likely to contain the random sample, the tree is pulled towards them (the "Voronoi bias"), and it spreads rapidly through the free space.

10.4 RRT-Connect: bidirectional growth

RRT-Connect (Kuffner and LaValle, 2000) grows two trees, one from the start and one from the goal, and tries greedily to join them:

if start or goal invalid:             return INVALID_START / INVALID_GOAL
if edge(start, goal) is valid:        return [start, goal]           # try_direct
Ta = tree(start); Tb = tree(goal)
while iterations, nodes and time remain:
    q_rand = uniform sample in the joint box (limits minus 0.05 rad)
    status, q_new = EXTEND(Ta, q_rand)            # one step of size <= 0.3 towards q_rand
    if status != TRAPPED:
        repeat: status_b = EXTEND(Tb, q_new)      # CONNECT: keep stepping towards q_new
        until status_b != ADVANCED
        if status_b == REACHED:                   # the trees touch at q_new
            return path(start ... q_new ... goal) # walk both trees back to their roots
    swap(Ta, Tb)
return TIMEOUT / NODE_BUDGET / NO_PATH

EXTEND(T, q):  q_near = nearest node of T (weighted metric)
               q_new  = q if d(q_near, q) <= step else q_near + step * (q - q_near)/d

Path reconstruction. Every node stores its parent's index (_Tree.parent). When the trees meet at a common configuration, following parent links from that node back to each root and joining the two branches gives the path: a list of configurations from start to goal, every consecutive pair joined by an edge that was checked when it was added.

10.6 Planning to a hand position: multiple IK postures

A Cartesian target has a 4-D family of joint solutions. Picking one posture and planning to it can fail even when another posture would be easy to reach. plan_to_position (motion_planner.py, line 129) therefore:

  1. checks the start;
  2. calls ik_candidates: 22 IK seeds (current, rest, 8 local perturbations with σ = 0.5 rad, 12 uniform random), keeps converged and collision-free solutions, de-duplicates them, sorts them by weighted distance from the start, keeps up to 4;
  3. reports unreachable if no seed converges and no_valid_ik if all converged postures are invalid;
  4. tries RRT-Connect to each candidate in order, giving each a fair share of the remaining time budget (unused time carries over), and returns the first success after shortcutting.
Reported result (v0.5 report §4)

10.7 Path smoothing

RRT paths zig-zag, because every edge points towards a random sample. shortcut (planning/shortcut.py) shortens them in two passes, keeping every edge collision-checked:

  1. Greedy pruning (prune): from each kept vertex, jump to the farthest later vertex reachable by a valid straight edge.
  2. Random shortcuts (100 seeded iterations): pick two points uniformly along the path, possibly inside edges; if the straight edge between them is valid and the new vertices and the shortened partial edges re-check as valid, splice it in. Then prune again and re-validate the whole path; if re-validation ever fails, return the original path unchanged.

There is no spline smoothing: the output is a polyline whose edges are exactly the straight joint segments the trajectory will execute, so nothing un-checked is ever executed.

Two bugs found and fixed in v0.5 (v0.5 report §5)

(1) Shortcuts were accepted using the weighted length while the unweighted length was reported: trading shoulder motion for wrist motion lowered one and raised the other, so "optimized" paths got longer with more iterations (1.49 rad at 50 iterations, 2.37 rad at 800). (2) A point on a validated edge is only certified to 15 mm, not 20 mm (Chapter 11), so new vertices failed final re-validation and long runs fell back to the raw path. After the fixes: 1.47 rad at 50, 1.45 at 100, 1.40 at 400 iterations.

10.9 Limitations

  • Not optimal. RRT-Connect plus shortcutting finds a path, not the shortest; lengths vary up to about 2× across seeds (thicker wall: 1.16–2.36 rad in v0.5.1). Optimal variants (RRT*, BIT*) are not implemented.
  • Static, known world. Obstacles are read from the model, known exactly, and assumed fixed during motion. Planning happens once, before motion; there is no replanning during execution.
  • Probabilistic completeness only. timeout, node_budget and no_path never prove that no path exists.
  • Rest-to-rest via points. The arm stops at every via point, which makes motions slower than a blended trajectory.
  • Position-only goals. Hand orientation at the goal is not planned; the gripper stays at its current opening.

Chapter 11Collision detection and clearance

The planner is only as trustworthy as its collision checker. This chapter explains how a configuration and an edge are judged safe, what the 20 mm clearance and the "15 mm" certificate really mean, and the story of the box-box near-miss bug found in v0.5.1 and fixed in v0.5.2.

11.1 Robot collision geometry

A physics engine does not collide the detailed visual meshes of a robot; it collides simpler collision geoms. For the Menagerie Panda, each link's collision shape is a convex mesh (MuJoCo uses the convex hull of each mesh), and each finger has one mesh plus five small boxes: a 17 × 8 × 17 mm fingertip pad and four 6 × 4 × 6–7 mm "teeth". The environment uses primitives: a plane (floor), boxes (table top and legs, wall, ceiling, obstacle_1) and a cylinder (obstacle_2).

11.2 Contact detection and minimum-distance queries

MuJoCo's mj_collision reports contacts: for each pair of geoms closer than their combined margin it creates a contact with a signed distance dist (negative means penetration). A different function, mj_geomDistance(m, d, g1, g2, distmax, fromto), returns the minimum distance between two specific geoms (up to distmax) and the two closest points. For convex shapes such distances are computed with the GJK algorithm, which iteratively searches the Minkowski difference of the two shapes for the point closest to the origin; penetration depth uses the related EPA algorithm.

11.3 Robot–environment versus self-collision

Two kinds of collision matter: the robot against the world and the robot against itself (for example the hand against the upper arm). MuJoCo filters pairs before testing them. Its contype/conaffinity bitmasks must match, bodies connected by a joint (parent and child) are not tested against each other, and explicit <exclude> pairs are skipped. The Menagerie model excludes link0–link1, and our engine adds an exclusion between the robot base and the table it stands on (build_spec, simulation/engine.py, line 66).

11.4 Safety margins and the configuration check

A configuration $q$ is valid (CollisionChecker.is_valid, planning/collision.py) if

  1. it lies inside the joint limits shrunk by 0.05 rad, and
  2. no robot geom penetrates another robot geom, and
  3. every robot–environment distance is at least the clearance $c$ = 20 mm.

How the clearance is implemented. The checker deep-copies the compiled plant model and sets geom_margin = 0.02 on every collidable environment geom. MuJoCo uses the larger of two geoms' margins for a pair, so robot–environment pairs now produce contacts already at distances below 20 mm, while robot–robot pairs keep margin 0 (self-collision means penetration). "Is there any robot contact?" then answers conditions 2 and 3 in one MuJoCo call. The plant model itself is never modified, and the checker writes only its own scratch data.

def _collide(self, q):
    d = self.data                       # private MjData of the private model copy
    d.qpos[:] = self.base_qpos          # fingers etc. as in the plant
    d.qpos[self.qpos_adr] = q
    mujoco.mj_kinematics(self.model, d)
    mujoco.mj_collision(self.model, d)  # contacts, with 20 mm margins on obstacles
    self.config_checks += 1

def in_collision(self, q):
    self._collide(q)
    return next(self._robot_contacts(), None) is not None   # any robot contact, incl. exact box-box (v0.5.2)
First MuJoCo pitfall (found in v0.5): the midphase ignores margins

A test sampling the executed demo found a configuration 8.8 mm from the wall, below the promised 15 mm. The cause was MuJoCo's midphase (per-body bounding-volume culling for multi-geom bodies such as the fingers), which does not account for the other geom's margin and dropped a finger–wall pair 8.5 mm apart under a 20 mm margin. Over 3,000 random configurations per scene it missed 14 of 91 and 16 of 74 near misses. The checker's model copy disables it (mjDSBL_MIDPHASE, line 119); with it off, 0 false negatives and 0 false positives against exhaustive mj_geomDistance (v0.5 report §2). test_checker_matches_exhaustive_distance_ground_truth guards this.

11.5 Collision checking along edges

The planner executes straight joint-space edges, $q(s) = q_0 + s(q_1 - q_0)$, $s \in [0,1]$. Checking a finite number of configurations on the edge leaves gaps; the question is how dense the samples must be. The checker derives the spacing from a bound on how far any point of the robot's collision geometry can move.

The lever-arm motion bound

A point $p$ on the robot moves, when joint $j$ rotates at rate $\dot q_j$, with velocity $\omega_j \times (p - o_j)$, where $o_j$ is a point on joint $j$'s axis. Its speed is at most $|\dot q_j|\,\|p - o_j\|$. Let $R_j$ bound the distance from joint $j$'s anchor to any collision geometry that joint $j$ moves, for every posture. Then along the edge, with $\dot q = q_1 - q_0$ per unit $s$:

\[ \left\|\frac{dp}{ds}\right\| \le \sum_j R_j\,|q_{1,j} - q_{0,j}| \qquad\Longrightarrow\qquad \text{path length of } p \text{ over the edge} \le \sum_j R_j |\Delta q_j|. \]

$R_j$ is computed in _lever_arms (line 166) by the triangle inequality, posture-independently: the distance from the joint anchor to its body origin, plus the chain of body offsets down to the geom's body (plus extra for off-origin hinges and slide ranges), plus the geom's offset and bounding radius. Values: [1.149, 1.149, 0.833, 0.751, 0.358, 0.358, 0.270] m.

The edge is split into $n$ intervals with

\[ n = \left\lceil \max\left( \frac{\sum_j R_j|\Delta q_j|}{\Delta_c},\; \frac{\max_j |\Delta q_j|}{\Delta_q} \right) \right\rceil, \qquad \Delta_c = 10 \text{ mm (cartesian\_step)}, \quad \Delta_q = 0.05 \text{ rad}. \] planning/collision.py, edge_samples, lines 200–204

so that no robot point travels more than 10 mm between consecutive samples. The interior samples are visited coarse-to-fine (midpoint first, then quarters, …; _coarse_to_fine), so a blocked edge is usually rejected after a few checks. Edge endpoints are checked separately.

11.6 The clearance certificate and its assumptions

Deduction

Claim. If every sample on an edge has robot–environment distance ≥ $c$, then every configuration on the edge has distance ≥ $c - \Delta_c/2$ = 15 mm.

Proof sketch. Take any configuration between samples $k$ and $k+1$ and any robot point $p$. Its path from sample $k$ to sample $k+1$ has length at most $\Delta_c$, so it is within $\Delta_c/2$ (along the path, hence in straight line) of its position at one of the two samples, where its distance to every obstacle was ≥ $c$. Distance to a set is 1-Lipschitz in position, so its distance now is ≥ $c - \Delta_c/2$. This holds for every point, hence for the robot.

Assumptions. (1) The per-sample answer "distance < $c$?" is exact. (2) The geometry is MuJoCo's convex collision shapes. (3) Obstacles do not move during the edge. (4) The robot follows the edge exactly. (5) It covers robot–environment pairs only: self-collision has margin 0 and is checked only at samples, so a brief self-intersection between samples is not excluded.

Assumption (4) is about execution, not planning. The controllers track the reference with errors well below 0.5 mrad on the planning scenes, i.e. tenths of a millimetre at the hand, which is small compared with the 5 mm margin between 20 and 15 mm, but it is a measured observation, not part of the proof. Assumption (1) failed for one pair type until v0.5.2, as the next sections explain.

11.7 The box-box near-miss issue (v0.5.1)

The discovery. While measuring clearances in the v0.5.1 wall-robustness experiment, the contact-based monitor reported 14.98 mm during one execution (thicker wall, seed 3), below the claimed 15 mm. Investigation showed a measurement problem rather than a near collision: for the fingertip pad (a box) against the box-shaped wall, MuJoCo's contact.dist said 14.64 mm while mj_geomDistance and an independent vertex-to-box computation both said 20.0 mm. At a neighbouring sample the error had the opposite sign: the checker accepted a configuration whose true distance was 19.94 mm, because no contact was generated at all.

Isolation. In an empty model with just a pad-sized box near a wall-sized box and a 20 mm margin, over 20,000 random poses: 260 of 14,568 poses within 30 mm had a true distance below 20 mm but produced no contact, the closest only 1.25 mm from the wall; where contacts were produced, contact.dist erred by −4.8 to +6.7 mm; actual penetration was always detected. The conclusion: MuJoCo 3.16's dedicated box-box routine does not produce reliable margin contacts. v0.5.1 documented the problem, pinned it with a strict expected-failure test, and left the planner unchanged because a planner change needed approval.

11.8 The investigation (v0.5.2)

Question. Which robot–environment pair types are affected, and is mj_geomDistance a trustworthy replacement? tools/audit_clearance.py builds, for each of 11 pair types in the scenes, an isolated two-geom model with the real Panda geometry (mesh vertices copied from the compiled model), the checker's solver flags and a 20 mm margin, and places the robot geom at 4,000 random poses within 40 mm of the obstacle.

Ground truth that does not trust MuJoCo.

  • Overlap is decided by a linear program (SciPy linprog): does some convex combination of the robot geom's vertices lie inside the obstacle? (For the cylinder, inscribed and circumscribed 64-gon prisms bracket the truth.)
  • Separation distance is certified by a duality gap: MuJoCo's witness points must lie inside their geoms (which proves an upper bound $\|a - b\|$), and the support functions of both shapes along the witness direction give a separating-plane lower bound $\min_{y\in B} n\cdot y - \max_{x\in A} n\cdot x$, valid for any direction $n$. When upper and lower bounds agree within 1 µm, the distance is proven, independently of how MuJoCo found the points.
  • A first attempt used a QP solver as ground truth. It disagreed with MuJoCo in 3 of 1,127 poses, but inspection showed the QP had not converged and MuJoCo was right; the certificate approach replaced it (worklog §2).

11.9 The fix

Three designs were considered: (a) replace mj_collision with mj_geomDistance for all ~150–180 robot–environment pairs (correct but about 250–480 µs per check instead of ~25 µs); (b) turn the fingertip boxes into box-shaped meshes in the checker's model (rejected: needs recompiling, and the checker should see the plant's exact geometry); (c) keep mj_collision for everything except box–box robot/obstacle pairs, ignore MuJoCo's contacts for those, and query mj_geomDistance for the ones a conservative bound cannot rule out. Option (c) was implemented.

Why the pre-filter is safe

The obstacle box is contained in its axis-aligned bounding box (AABB). Every point of the robot box lies within its bounding radius $r$ of its centre $p$. If $p$ lies outside the AABB grown by $c + r$ along some axis, then $p$ is at least $c + r$ from the AABB in that coordinate, hence at least $c + r$ from the obstacle, and every point of the robot box is at least $c$ from the obstacle. So skipped pairs are provably at least the clearance apart; the filter can cause extra queries but never a missed violation.

Chapter 12Trajectory generation and execution

A planner returns a route; a controller needs a schedule. This chapter explains how routes become smooth, limit-respecting functions of time, and why a collision-free path is not automatically a feasible motion.

12.1 Path versus trajectory

A path is a geometric curve in configuration space with no notion of time: "go from A through B to C". A trajectory is a path with timing: the configuration as a function of time, $q(t)$, and therefore also velocities $\dot q(t)$ and accelerations $\ddot q(t)$. The planner produces paths (polylines of joint configurations); the task layer turns them into trajectories; the controller tracks the trajectory.

12.2 Time parameterization of a straight joint move

Every move in the project is a straight joint-space line traversed with a scalar timing law $s(t)$ that goes from 0 to 1:

\[ q(t) = q_a + (q_b - q_a)\,s(t), \qquad \dot q(t) = (q_b - q_a)\,\dot s(t), \qquad \ddot q(t) = (q_b - q_a)\,\ddot s(t). \]

Only the timing law changes, never the geometry, so the trajectory follows exactly the edge that the collision checker validated. Because the joint-limit box is convex and $s$ goes monotonically from 0 to 1, $q(t)$ stays inside the joint limits if both ends do. Per joint, $|\dot q_j| = |\Delta q_j|\,|\dot s|$, so all seven velocity limits collapse into one scalar limit on $\dot s$: $v_s = \min_j v_{\max,j}/|\Delta q_j|$. The joint with the largest motion relative to its limit is the binding one. The same holds for acceleration ($a_s$) and jerk ($j_s$).

12.3 Smoothness: the minimum-jerk quintic

Intuition. A motion that starts and stops abruptly demands infinite acceleration. We want $s$ to start and end at rest with zero acceleration, so the reference is smooth at the joints of consecutive segments. With normalized time $\tau = t/T$ these are six boundary conditions:

\[ s(0) = 0,\; s(1) = 1,\; s'(0) = s'(1) = 0,\; s''(0) = s''(1) = 0. \]

The lowest-degree polynomial satisfying six conditions has degree five. Writing $s(\tau) = a_3\tau^3 + a_4\tau^4 + a_5\tau^5$ (the conditions at 0 force $a_0 = a_1 = a_2 = 0$) and imposing the three conditions at $\tau = 1$ gives $a_3 + a_4 + a_5 = 1$, $3a_3 + 4a_4 + 5a_5 = 0$, $6a_3 + 12a_4 + 20a_5 = 0$, whose solution is

\[ s(\tau) = 10\tau^3 - 15\tau^4 + 6\tau^5 . \]

This polynomial also minimizes the integral of squared jerk over the move, hence "minimum-jerk". Its peaks are $\max s' = 1.875$ (at $\tau = 0.5$), $\max|s''| = 10/\sqrt3 \approx 5.7735$ and $\max|s'''| = 60$. In real time, with duration $T$:

\[ \max|\dot q_j| = \frac{1.875\,|\Delta q_j|}{T}, \qquad \max|\ddot q_j| = \frac{5.7735\,|\Delta q_j|}{T^2}, \qquad \max|\dddot q_j| = \frac{60\,|\Delta q_j|}{T^3}. \]

So the shortest feasible duration for given limits is

\[ T_{\min} = \max\left( \frac{1.875}{v_s},\; \sqrt{\frac{5.7735}{a_s}},\; \sqrt[3]{\frac{60}{j_s}} \right). \] tasks/trajectory.py, constants lines 47–49; plan_segment lines 220–226

The quintic is $C^2$ (position, velocity and acceleration are continuous, also across segments, since every segment starts and ends at rest with zero acceleration); its jerk jumps at segment boundaries.

12.4 The double-S profile

The quintic touches its speed limit only for an instant at mid-move. The double-S (jerk-limited) profile instead has seven phases of constant jerk ($+j, 0, -j, 0, -j, 0, +j$): it ramps acceleration up, accelerates, ramps down, cruises at the speed limit, and mirrors that to stop. It is the time-optimal rest-to-rest profile under velocity, acceleration and jerk limits (Biagiotti & Melchiorri, 2008, §3.4), so at the same limits it is faster than the quintic, at the price of a jerk that is only piecewise constant. DoubleS (tasks/trajectory.py, line 90) computes the phase durations for the three cases (speed limit reached; too short to cruise; acceleration limit not reached either) and integrates the phases exactly (end error ~1e-15, tested).

12.5 Trajectory scaling and actuator feasibility

plan_segment(start, goal, requested_time, limits, profile, torque_fn, torque_limits) (line 189) returns the shortest move that is no shorter than requested and respects the limits:

  1. check both endpoints against the joint limits (raise TrajectoryInfeasible otherwise);
  2. compute $v_s, a_s, j_s$ and the minimum duration for each limit; if any exceeds the requested time, lengthen the move to it and record which limit and joint set it (limited_by, limiting_joint);
  3. if a torque function is given, sample inverse dynamics at 101 points along the move. If any joint exceeds its torque budget, stretch time by $f = \max(1.05, \sqrt{\max(\text{dynamic torque}/\text{room})})$, because a uniform time stretch by $f$ scales velocity by $1/f$, acceleration by $1/f^2$ and the dynamic part of the torque roughly by $1/f^2$, while gravity torque does not change. If gravity alone exceeds the budget somewhere on the path, no duration helps: raise TrajectoryInfeasible.
Configuration used by main.py tasks

task.trajectory in configs/default.yaml, reach.yaml and planning_demo.yaml: profile min_jerk, velocity 0.9, acceleration 0.5, jerk 0.05 (the datasheet jerk limits of 3,750–10,000 rad/s³ are far above what smooth tracking needs) and torque 0.8 of the limits. The torque function is ArmInverseDynamics.torque on the controller's model; the budget is 0.8 × the plant's force range (SimulationRunner.trajectory_options). Without the section, tasks reproduce the old fixed-duration quintic bit for bit (test_unlimited_task_reproduces_v03_quintic).

Example: the generator's choices (v0.4 report §3)

fast_feasible requests 1.0 s moves between the demo poses. The generator lengthened them to 1.585 s (joint 7 velocity limit), 1.341 s (joint 1 velocity) and kept 1.000 s for the last. wrist_feasible: 2.223, 3.193, 2.000 s. With the double-S profile the 2 s moves stayed at 2 s (cruising at ≤ 0.9 $v_{\max}$). An infeasible budget is reported in words, e.g. "joint 2 needs 35.2 Nm just to hold against gravity (budget 8.7 Nm): no duration is feasible" for a 10% torque budget.

12.6 How paths become MPC tracking references

CartesianReachTask and PlannedJointTask turn each planned path into waypoints: the interior vertices become via points with zero hold time, and the goal gets the configured hold. Each edge requests segment_time (1.0 s) and is then time-scaled as above. The result is an ordinary JointTargetTask, whose reference(t) returns $q_{\text{ref}}(t), \dot q_{\text{ref}}(t), \ddot q_{\text{ref}}(t)$:

  • the runner calls it once per physics step for the controller's current reference;
  • the torque MPC additionally calls it, through reference_preview, at 25 future times every update;
  • CTC uses $\ddot q_{\text{ref}}$ as acceleration feedforward.

Because every via point is a rest-to-rest stop, the trajectory passes exactly through every vertex and stays on the checked edges; the price is that the arm stops at each via point. If a planned move is just the free direct edge, it keeps the ordinary move_time, so enabling planning leaves unobstructed tasks identical to the unplanned behaviour (test_planning_on_free_joint_moves_matches_unplanned_task).

Example from the planning benchmark (v0.5 report §6, §8)

Wall scenario, three seeds: planned motion durations 3.00, 5.00 and 3.00 s; the end effector came within 1 mm of the target at 2.93, 4.88 and 2.93 s, for both controllers to within 0.01 s. test_planned_reference_is_continuous_feasible_and_collision_free checks that the demo reference is continuous, within the speed/acceleration/jerk limits, passes through every vertex and keeps at least 15 mm from the environment at every sample.

12.7 Why a collision-free path is not automatically dynamically feasible

Collision checking is purely geometric: it asks whether postures overlap obstacles. Whether the motors can actually produce the motion depends on speed and posture. A collision-free path executed too fast exceeds speed limits; executed through a posture where gravity alone needs more torque than the motor has, it is infeasible at any speed. The v0.3 benchmark references fast and wrist were geometrically harmless but demanded 1.43× the joint-7 speed limit (Chapter 9). The planner validates geometry; the trajectory generator validates speed, acceleration, jerk and torque. Both are needed, and they are applied in that order.

A side effect worth knowing (v0.5 report §7)

With the path collision check deliberately disabled, the torque-feasibility check still rejected a move through the wall ("joint 1 needs 140903 Nm"): MuJoCo's inverse dynamics includes contact forces where the reference penetrates the obstacle. This is an accident of the implementation and samples only 101 points; it is not a collision check, and the unsafe comparison mode --unchecked-direct disables it explicitly.

12.8 Limitations

  • Rest-to-rest segments: no blending through via points, so planned motions are slower than necessary.
  • Straight joint-space segments only; no Cartesian straight lines, no orientation profiles.
  • The torque check samples 101 points and uses the controller's model; it is a design-time check, not a guarantee during execution.
  • Time scaling is uniform per segment (whole segment slowed), not time-optimal path parameterization along the path.

Chapter 13Software architecture and modularity

Which parts of the code could be swapped out cleanly, which are merely in separate files, and which are tightly bound to the Panda and to MuJoCo. The second half asks what it would take to substitute major components; everything there is a proposal.

13.1 The intended layering

The project's stated rules (CLAUDE.md, "Conventions and rules") are: environments know nothing about robots; tasks produce references only; controllers produce actuator commands only; settings belong in YAML; the prediction model never writes live simulation data; motion comes only from data.ctrl + mj_step. The import graph (Chapter 2) shows these rules are largely respected.

13.2 What is truly modular

  • Controllers behind one interface. All four implement Controller.compute(q, qd, q_ref, qd_ref, dt, t, qdd_ref) and reset(); the runner and benchmarks treat them uniformly; a new controller needs one class and one branch in build_controller. Controllers never import tasks, planners or the engine; future references arrive through the injected reference_preview callable.
  • Tasks as reference generators. Every task exposes reference(t), duration, waypoints and timing information (an implicit, duck-typed interface; there is no abstract base class). The planner is injected as a function (plan=planner.plan_to_position), so tasks do not depend on planning/.
  • Environments independent of robots. Scene files only need a robot_mount site and a target mocap body; the robot is attached in code.
  • Configuration-driven runs. Environment, task, controller, planner settings, mismatch, noise and geometry overrides all come from YAML, so experiments are data, not code.
  • Planner invisible to controllers. Planning produces an ordinary joint reference; the same plan runs under any controller.

13.3 What is only separated into files

  • The robot. Panda is a dataclass of names and limits, and SimulationEngine reads its fields (joint names, actuator names, base body, end-effector site). But Panda specifics leak elsewhere: the end-effector offset, the gripper command 255, the actuator conversion in _make_torque_actuators (assumes seven general actuators with a home keyframe), the finger handling in the prediction model (it composes only the arm block), and the 7-joint shapes assumed in tests and configs.
  • Controller selection. CONTROLLER_TYPES, CONTROLLER_ACTUATION and the build_* functions in runner.py are a hand-written factory; adding a controller means editing the runner.
  • Experiment drivers. The three benchmark modules share patterns (config building, CSV writing) but not code; they import specific controller classes to read their statistics.

13.4 What is tightly coupled

  • MuJoCo everywhere. The prediction model (mjd_transitionFD, rollouts), inverse dynamics (mj_inverse), the observer (mjENBL_INVDISCRETE), kinematics (mj_kinematics, mj_jacSite), the collision checker (mj_collision, mj_geomDistance, margins, midphase flag) and the benchmarks all take MjModel/MjData directly. This is a deliberate strength (the controller model is exactly the simulator's dynamics) and the main obstacle to changing simulator.
  • Torque MPC on servo-MPC internals. torque_mpc.py imports MPCStats, MPCUpdate, plan_violations and the private helper _per_joint from mpc.py.
  • Planning on simulation code. planning/ik.py and motion_planner.py use simulation.kinematics.ArmKinematics, and the checker is built from a SimulationEngine (from_engine).
  • Benchmark cycle. simulation/robustness.py imports planning_benchmark, which imports robustness lazily inside a function for ExactClearance.
  • Special names. The engine excludes contact between the robot base and a body literally named table.

15.11 Statistical limitations

How much does "0 failures" prove?

If an event has probability $p$ per trial, the chance of seeing zero events in $n$ independent trials is $(1-p)^n$. Setting this to 5% gives the "rule of three": with 95% confidence, $p \lesssim 3/n$. For the wall-variant experiment's 0/30 planning failures this bound is about 10%; for 0/60 execution failures about 5%; for the planning benchmark's 0/20 per scenario about 15%. These experiments therefore show the methods work in these settings; they do not show failure rates below a few percent. (And the trials are not fully independent: same start, target and machine.)

  • Deterministic single runs. Controller benchmarks are deterministic: re-running gives identical tracking numbers. That makes them excellent regression tests but means each scenario is a sample of one trajectory, not a distribution.
  • Narrow task families. One wall geometry family, one start, one target; a handful of waypoint sets.
  • Timing is not reproducible. Wall-clock numbers vary 2–3× with machine load; only iteration counts and node counts are exact.
  • Measurement instruments changed. v0.5/v0.5.1 clearance columns used MuJoCo contacts (inaccurate for box-box pairs); v0.5.2 columns are exact. Clearance numbers across versions are not directly comparable.

15.12 Reproducibility

All simulations start from fixed states, all random choices use fixed seeds, and versions are recorded in every results file. The v0.4 report re-ran the v0.3 baseline and matched every tracking and constraint metric (MPC differences ≤ 1.6e-9 rad from floating-point round-off). v0.5.2 re-ran v0.5.1's planning in v0.5 mode and reproduced all 30 path lengths exactly. Planning is deterministic as long as no wall-clock budget ends a search. Raw outputs go to the git-ignored results/; copies of the key tables are committed as CSV in docs/research/. Benchmarks are not tests. The benchmark scripts measure performance and write numbers; they assert nothing about the numbers. Tests assert properties (often with generous thresholds, such as "tracking error below a bound") so that they are robust to small numerical changes.

16.3 Mathematical guarantees versus empirical observations

A test can only check finitely many cases. Some tests check a property that is also proven (the lever-arm bound holds for every posture by the triangle inequality; the test confirms the implementation matches the proof on random edges). Others check an observation with no proof behind it (that the torque MPC tracks the demo below a threshold; that the checker agreed with mj_geomDistance on 500 configurations). Neither kind proves correctness in general. The project's documentation is careful about this distinction; the planner's "15 mm" is a deduction with assumptions (Chapter 11), and the controllers' stability is empirical (Chapter 8).

16.4 What the tests do not validate

Gaps
  • Real-time behaviour. No test checks timing; deadline overruns are only reported by benchmarks.
  • Quantitative benchmark claims. The numbers in the reports are not asserted anywhere; a regression that worsened tracking from 2.8 µrad to 50 µrad could pass the suite if it stays under a test's threshold.
  • Viewer mode. run_viewer and its Windows thread-join workaround are not exercised (only path drawing into a scene, headless).
  • Self-collision between samples, and robot–environment clearance during execution beyond the specific runs tested.
  • Breadth of scenarios. Planning tests use a few scenes and starts; there is no randomized scenario generation or long-run statistics.
  • Realistic sensing. Only white Gaussian noise; no quantization, delay, filtering, or dropped measurements.
  • Model error beyond mass scaling (friction, damping, armature, centre of mass).
  • Servo MPC quality. Tests check it runs and falls back correctly, not that it tracks well (it does not, compared with PID).
  • Optimality of QP solutions for the torque MPC (the objective audit tool exists only for the servo MPC).
  • Documentation commands. Commands in README/reports are not executed by tests.
  • Grasping, pick-and-place, perception, replanning during motion: not implemented, hence not tested.

18.1 RGB cameras

A colour camera measures, for each pixel, the light arriving from one direction. The pinhole model relates a 3-D point $(X, Y, Z)$ in the camera frame to its pixel $(u, v)$:

\[ u = f_x \frac{X}{Z} + c_x, \qquad v = f_y \frac{Y}{Z} + c_y, \]

with focal lengths $f_x, f_y$ and principal point $(c_x, c_y)$ in pixels (the intrinsics). Depth $Z$ is lost: a single image cannot tell a small near object from a large far one. RGB images are rich in appearance information (what an object is) but poor in geometry.

18.2 Depth cameras and point clouds

A depth camera (stereo, structured light or time-of-flight) also measures $Z$ per pixel. Inverting the pinhole model turns each pixel into a 3-D point, $X = (u - c_x)Z/f_x$, $Y = (v - c_y)Z/f_y$; all pixels together form a point cloud. MuJoCo can render depth images (mujoco.Renderer with depth rendering), so a simulated depth camera could be added without new dependencies; in this project the renderer is used only for the demo video (tools/render_demo_video.py).

18.3 Coordinate transforms

Points measured in the camera frame must be expressed in the world (or robot base) frame before the planner can use them: $p_W = T_{WC}\,p_C$ with the homogeneous transform of the camera (its extrinsics, Chapter 4). For a camera mounted on the hand, $T_{WC} = T_{W,\text{hand}}(q)\,T_{\text{hand},C}$ depends on the joint angles: forward kinematics again. Errors in $T_{WC}$ (calibration) shift every obstacle, so they must be smaller than the clearance margin.

18.4 Object detection and environment reconstruction

Object detection finds and labels objects in images (classically with features, today mostly with neural networks), giving bounding boxes or masks. Reconstruction turns depth data into geometry usable for collision checking. Common representations: fitted primitives (boxes, cylinders) for known object types; voxel grids or octrees (OctoMap) marking occupied space; signed distance fields (each voxel stores the distance to the nearest surface), which give distance queries directly; and meshes.

18.5 World models

A world model is the robot's current belief about its surroundings: which objects exist, where they are, how certain that is, and when it was last observed. The planner should query the world model, not the sensors directly. In this project the "world model" is implicit: the MuJoCo model compiled at episode start, possibly modified with environment_overrides.

18.6 Uncertainty and occlusion

Perception is never exact: depth noise grows with distance, edges are blurred, reflective or transparent surfaces fail, and occlusion hides whatever is behind other objects (including behind the robot's own arm). A safe planner must treat unobserved space as possibly occupied and inflate observed obstacles by the measurement uncertainty. The 20 mm clearance, which today only absorbs discretization and tracking error, would have to absorb perception error as well; Chapter 11's certificate assumed exact geometry.

18.7 Sensor feedback and detecting obstacles while moving

Cameras run at 10–60 Hz with tens of milliseconds of latency, far slower than the 500 Hz control loop. Detecting a new obstacle during motion requires: continuously updating the world model; checking the remaining part of the current plan against it (the existing CollisionChecker.path_valid does exactly this for old plans, Chapter 15, E8); and, if it is no longer valid, stopping safely or replanning (Chapter 19).

18.8 Connecting perception to our planner

A possible design
  1. Render RGB-D images from one or two simulated cameras in MuJoCo at 10–30 Hz.
  2. Convert depth to a point cloud in the world frame using the known camera pose.
  3. Remove points belonging to the robot (render a robot mask, or test points against the robot's collision geometry at the current $q$).
  4. Fit boxes to clustered points (the scenes' obstacles are boxes and a cylinder), or build a voxel/distance grid.
  5. Write the result into the planner's model: for boxes, through geometry overrides (as v0.5.1 does with exact values today); for grids, through a new CollisionWorld backend (Chapter 13) that answers distance queries.
  6. Inflate obstacles by an uncertainty margin and re-run the audit methodology of v0.5.2 on the new distance queries before claiming any clearance.

A natural first experiment, in the spirit of v0.5.1: repeat the wall-variant experiment with geometry estimated from simulated depth images instead of given exactly, and measure how the estimation error must be absorbed by the clearance.

Chapter 19Reactive planning and autonomous manipulation

Status

None of the architecture in this chapter is implemented. It is a design discussion grounded in the current code.

19.1 A layered autonomy stack

19.2 World-model updates and reactive replanning

With perception updating the world model, a monitor would re-check the remaining part of the current path at every world-model update (cheap: path_valid on a few edges; tens of milliseconds at the measured 35–67 µs per configuration check). If it becomes invalid, three responses are possible, in increasing sophistication: stop safely; replan from the current state; or locally deform the trajectory. Replanning from a moving state is the hard part: today's planner assumes a start at rest at a waypoint.

19.3 Trajectory updates and controller continuity

Swapping in a new trajectory while the arm moves must not create a jump in the reference, or the MPC will see a step and the torque will jerk. Standard approaches: start the new plan from the state predicted at the switching time (position and velocity), blend over a short window, or plan with the current velocity as an initial condition. The torque MPC helps here: its reference preview means a new reference can be fed in through reference_preview without restarting the controller, and its warm start keeps the optimization continuous. Today's rest-to-rest segments cannot represent a non-zero starting velocity.

19.4 Safety monitoring and safe stopping

A safety monitor is an independent, simple layer that can override everything above: if the predicted state violates a limit, the measured distance to an obstacle drops below a threshold, or the planner fails to deliver, it commands a controlled stop. A controlled stop needs a stopping trajectory that is itself feasible (speed and torque limits) and collision-free; with the current speeds the stopping distance is short but not zero. The MPC could implement "stop" simply as a reference that holds the current position, with its torque limits guaranteeing feasibility of the command (not of the stop distance).

19.5 Obstacle-aware MPC

An alternative to replanning is to give the MPC itself obstacle constraints, for example linearized distance constraints $d(q_k) \ge c$ approximated as $d(\bar q_k) + \nabla d(\bar q_k)^T(q_k - \bar q_k) \ge c$ around the previous plan. This keeps the QP convex but is only locally valid, and the 0.5 s horizon cannot find detours around large obstacles. In practice it complements a global planner (the planner finds the route; the MPC keeps a margin locally). It would require distance gradients, which MuJoCo can provide through mj_geomDistance's witness points.

19.6 Grasp planning and contact-rich manipulation

Grasping adds requirements the current system lacks:

  • Orientation. IK must solve for the full hand pose (6-D), not just position.
  • Intentional contact. The collision checker must allow fingers to touch the object being grasped (contact exclusions per phase).
  • Gripper control. Actuator 8 must close with controlled force; finger states are currently frozen in the prediction and collision models.
  • Changing dynamics. A grasped object changes the arm's payload. The disturbance observer would partially absorb an unknown payload (it did for a 30 N downward load ≈ 3 kg, Chapter 9), and the object must join the robot's collision geometry.
  • Contact-rich control. Pushing, inserting or wiping need force or impedance control (regulating contact forces rather than positions), which neither the CTC nor the MPC currently provides.

19.7 High-level AI agents

A language-model or learned task planner could decide what to do ("clear the table") and emit goals to the motion layer. The clean interface is narrow: goals (target poses, grasp/release commands) go down; status (reached, rejected with reason, failed) comes up. The existing motion layer already returns explicit rejection reasons ("collision on path", "IK did not converge"), which is exactly the kind of feedback such an agent needs. Safety must remain in the lower layers: an agent's request should never bypass the collision checker or the torque limits.

Chapter 20Research readiness and future directions

An assessment of Robotics Lab as a research platform: genuine strengths, weaknesses, technical debt, valuable next experiments, and a possible v0.6 direction. Opinions in this chapter are the author's assessment based on the evidence in the previous chapters.

20.1 Genuine technical strengths

  • Measurement discipline. Metrics come from the simulated robot, not from controller predictions; failures are reported with every run; historical baselines are preserved; versions and seeds are recorded. This is rarer in student and even research code than it should be.
  • Independent verification culture. Twice, results were checked against an independent measurement and a simulator behaviour was found that invalidated a claim (midphase, box-box margins). The v0.5.2 audit used certificates rather than a second numerical solver, which is methodologically sound.
  • A strong, exact low-level controller. A torque MPC built directly on MuJoCo's discrete dynamics with hard torque limits, normalized variables, offset-free disturbance estimation and validated fallback, achieving µrad tracking in nominal conditions.
  • Clear separation between planning and control, with stated and tested assumptions (the planner is invisible to the controllers; the reference stays on checked edges).
  • Explicit, honest limitations in every report.

20.2 Engineering weaknesses

  • Exact-model optimism. Nominal results use the plant's own model; only uniform mass errors were tested.
  • Narrow scenarios. One wall family, a few waypoint sets, 5–20 seeds per condition.
  • Single-threaded Python on a desktop OS. Timing is noisy and not real-time; 100 Hz MPC does not fit.
  • No perception, no reactivity, no manipulation (Chapter 17).
  • Servo MPC remains worse than PID and has no current purpose beyond documentation.

20.4 What is standard engineering, and what could be scientifically interesting

Standard (well-known methods, carefully implemented): DLS inverse kinematics, computed-torque control, linear MPC with OSQP, disturbance observers, RRT-Connect with shortcutting, quintic and double-S time scaling, margin-based clearance. None of these is new; their value here is the integration and the measurements.

Potentially interesting, if pursued rigorously:

  • Reliability of simulator geometry queries for safety claims. The finding that a mainstream simulator's margin contacts are wrong for some primitive pairs, and the certificate-based audit, generalize: any planner that uses a physics engine's contact margins for clearance should audit them. A systematic study across engines and shape pairs would be a useful contribution.
  • Certified clearance under tracking error. Combining the discrete edge certificate with measured or bounded tracking error of the torque MPC to state an execution-level clearance bound.
  • When does torque MPC beat CTC + observer? The data show MPC wins nominal tracking and constraint handling while CTC + observer wins disturbance rejection; characterizing the trade-off (noise, delay, model error) is a well-posed controlled study.
  • Perception-in-the-loop margins: how clearance must grow with depth-estimation error (Chapter 18's experiment).

20.5 The most valuable next experiments

  1. Realistic sensing and delay: encoder quantization, velocity filtering, one control period of computation delay; re-tune and compare MPC and CTC + observer.
  2. Richer model error: friction, damping, armature, centre of mass, payload; test the observer's limits.
  3. Randomized planning scenarios (random obstacles, starts and goals) with hundreds of episodes, to estimate failure rates below the few percent the current samples can bound.
  4. Blended trajectories through via points (with the blended curve collision-checked), measuring time saved.
  5. LTV/SQP-RTI prediction to reduce the k³ growth of open-loop prediction error, and its effect on constraint predictions.

20.6 Connecting to autonomous-manipulation research

Most current manipulation research combines learned components (perception, grasp prediction, policies trained by imitation or reinforcement learning) with model-based layers for safety and precision. Robotics Lab's motion layer is a reasonable model-based bottom layer: a learned policy could output goals or short reference segments, the planner and collision checker would act as a safety filter, and the torque MPC would execute. The evaluation harness (seeded episodes, exact clearance, contact counts, explicit failure statuses) is directly reusable for evaluating such policies. The prerequisite is a manipulation task (objects, grasping) and, for learning, many fast simulated episodes, which raises the cost of the current Python MPC.

20.7 An appropriate v0.6 direction

Proposal — not started

The project's own plan names pick-and-place next. A focused v0.6 could be a minimal, measured pick-and-place in a known world:

  1. add one graspable box to a scene and a stable placement target;
  2. extend IK to full 6-D pose (position + orientation) for top-down grasps;
  3. phase-dependent collision rules (allow finger–object contact during grasp; treat the grasped object as robot geometry while carrying);
  4. close the gripper through actuator 8 and verify grasp success physically (object lifts, does not slip);
  5. carry with the disturbance observer absorbing the payload; measure tracking with and without the observer;
  6. evaluate over seeded object poses: success rate, contacts other than the grasp, clearance, placement error.

This uses every existing layer, adds the missing manipulation pieces one at a time, and keeps the project's discipline of measured, reproducible claims. Perception and reactive replanning would naturally follow as v0.7+.

The part of a command computed from the reference in advance, not from the error.

Computing the hand pose from joint angles.

Algorithms for the distance (GJK) and penetration depth (EPA) between convex shapes.

Computing the torque needed for a given acceleration (mj_inverse).

Finding joint angles that place the hand at a desired position.

The matrix mapping joint velocities to hand velocity, $\dot x = J\dot q$.

The time derivative of acceleration.

Approximating a nonlinear map by a linear (affine) one near an operating point.

A MuJoCo body moved kinematically by code; here the visual target marker.

Control by repeatedly solving a finite-horizon optimization with a model and applying the first command.

The physics engine simulating the robot (version 3.16).

Joint motions that do not move the hand; used to steer a redundant arm's posture.

Control without steady-state error under constant disturbances.

The quadratic-programming solver used by both MPCs.

A geometric route (no time) / a route with timing $q(t)$.

Proportional–integral–derivative feedback control.

The system being controlled: the simulated Panda.
Polishing
An OSQP step that refines an approximate solution to high accuracy.

An actuator that pulls a joint towards a commanded angle with a stiff spring-damper.

The property that the chance of finding an existing path tends to 1 as sampling continues.

Minimize a quadratic cost subject to linear constraints.

Re-planning at every step over a window that moves forward with time.

Having more DOF than the task needs (7 joints for a 3-D position goal).

The desired trajectory the controller tracks.

Workspace
The set of hand positions the robot can reach.

The robot's belief about its surroundings (implicit here: the MuJoCo model).

Appendix ECommon questions

E.1 Does our MPC learn?

No. It has no trainable parameters and uses no data. At every update it linearizes MuJoCo's equations at the measured state and solves an optimization problem from scratch (Chapter 7). The only "memory" between updates is the warm start (the previous solution as a starting guess) and the disturbance observer's filtered estimate, which is an estimator, not learning.

E.2 How does the robot know the wall exists?

It is told. The wall is a box in environments/planning_demo.xml; the planner's collision checker deep-copies the compiled MuJoCo model, wall included, and queries it. There is no sensing. In the wall-variant experiment the new geometry is passed in through environment_overrides, again exactly.

E.3 Does the controller run continuously?

In simulated time, yes: compute() is called every 2 ms of simulated time; the torque MPC re-solves every 20 ms and holds (and observer-corrects) its torque in between. In wall-clock time, no: headless runs advance as fast as the computer allows, and the viewer slows the simulation to match the wall clock. If computation is too slow, simulated time simply waits.

E.4 Why do we need RRT if we already have MPC?

They solve different problems. RRT-Connect searches the whole 7-D configuration space for a collision-free route, which is a global, non-convex problem. The MPC optimizes torques over the next 0.5 s to follow a given reference within motor limits, which is a local, convex problem with no knowledge of obstacles. Neither could do the other's job (Chapter 9, §"Why closed-loop MPC does not give obstacle avoidance").

E.5 Does the simulation use a GPU?

No. MuJoCo's physics, the planner and the OSQP solver all run on the CPU in a single process. The GPU is used only through OpenGL for drawing the interactive viewer and rendering the demo video.

E.6 What happens if the robot hits an obstacle?

MuJoCo computes contact forces, so the arm is physically stopped and pushed, as in reality. Nothing in the software reacts to it: the controller keeps trying to track the reference and pushes into the obstacle. The unsafe baseline shows this: 1,005–1,849 contact steps, the arm stuck 175–470 mm from the goal (Chapter 15). In planned runs, success is defined as zero contact steps, which every planned execution achieved.

E.7 Why is 50 Hz different from 500 Hz?

500 Hz is the physics rate (2 ms steps) and the rate at which PID, CTC and the observer act. 50 Hz is the torque MPC's re-planning rate: each QP takes about 5 ms to solve, so solving one every 2 ms is impossible in this implementation. Between MPC updates the torque is held, with a 500 Hz correction from the observer. A 100 Hz MPC with an equivalent 0.5 s horizon did not fit its 10 ms budget (Chapter 9).

E.8 Can this system control a real robot?

Not as it is. It has no hardware interface (the Panda is usually driven through Franka's real-time control interface at 1 kHz), no real-time guarantees (Python on Windows), no safety layer, and its controllers were tuned on an exact model with perfect sensors. The ideas transfer; the code would need a real-time implementation, state estimation, friction and payload identification, safety monitoring, and re-validation on hardware.

E.9 What makes a robotics project research-quality?

A clear question; a baseline to compare against; controlled experiments where one thing changes at a time; metrics measured on the system rather than on the algorithm's own predictions; enough runs to support the claim, with uncertainty stated; reproducibility (seeds, versions, commands); honest reporting of failures and limitations; and, ideally, results that hold beyond the specific set-up. This project does many of these well (baselines, controlled comparisons, independent measurements, reproducibility, honest limitations) and is weaker on sample sizes, breadth of scenarios and hardware validation (Chapter 20).

E.10 Why do the torque controllers look 1000× better than PID?

Mostly because of the actuator model, not the algorithm: PID drives stiff position servos whose setpoint steps and gravity sag limit accuracy, while the torque controllers command torque directly with an exact model of the plant. Comparisons are only fair within the same actuator group (Chapter 6).

E.11 Is the 15 mm clearance guaranteed?

It is a mathematical deduction that holds under stated assumptions: exact per-sample distances (audited for these shapes, not proven), MuJoCo's collision geometry, static obstacles, and exact tracking of the edge. It covers robot–environment pairs only. What was measured is stronger in practice (≥ 19.998 mm on the benchmark paths), but measurements are not guarantees (Chapter 11).
